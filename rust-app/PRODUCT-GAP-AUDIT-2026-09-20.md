# 🍑sh harness 产品功能差距核对

核对日期：2026-09-20。对象：D:\peachsh-harness 的 Rust 0.2.0 主应用。目标：面向个人开发者、以 xpeach 多 Key / 多模型协作为特色的本机编程产品。

## 1. 结论与核对口径

当前应定位为“已跑通核心技术链路、正在补齐日常开发闭环的开发预览版”。已经具备真实模型对话、手工多模型任务、文件工具、依赖调度和持久化；本轮已把对话工具权限、失败草稿、停止、文件恢复和四项已知安全/可靠性探针接入主线，但还没有完成普通用户从打开项目到验收、交付修改的完整流程。不能因为 Rust 测试通过、模型返回成功、WASM 示例可运行，就把 DSH 产品迁移标记为完成。

本轮执行了源码核对、当前实例健康检查，以及 Codex、Claude Code、官方开源 DSH 文档比对；没有重新执行所有故障注入或付费模型请求。既有实测引用 [实机评估报告](ASSESSMENT-LIVE-2026-09-20.md)，新发现的界面问题明确标为源码确认或待复现。

- 当前 3090 实例健康：Rust 0.2.0，SQLite schema 4；本轮最终发布 EXE SHA-256 为 `18B57585172BF53AACC0FDB25461677A8D97A74343AD898B60676BB9FA87A17D`。
- 本机旧版安装清单锁定 DSH 0.1.6-alpha.2。下面 DSH 对标引用的是核对当天的官方在线文档，可能领先于这个旧版；不能据此声称 0.1.6-alpha.2 拥有所有列出的能力。
- “已有”表示当前 Rust 主入口提供；“部分”表示只有底层能力或流程不完整；“缺失”表示在核对的主程序接口、工具注册与界面中未实现；“旧版保留”不计为 Rust 已迁移。
- 优先级为产品交付顺序：P0 是第一版可日常使用的前置条件；P1 是核心竞争力和持续使用能力；P2 是体验及扩展；P3 是明确需要后再做。此定义与既有缺陷报告的安全严重级别不同。

## 2. 三个参考产品分别学什么

| 参考 | 官方资料确认的能力 | 对 🍑sh 的借鉴 |
|---|---|---|
| Codex | 可审阅代码差异，并衔接暂存、撤销、提交与推送 | 用户必须看得清改动，并有明确交付入口。[官方代码审阅](https://learn.chatgpt.com/docs/code-review) |
| Codex | Git worktree 支持同项目多个独立会话；有子代理编排、跟进和结果回收 | 团队协作需要工作区隔离和代理生命周期。[Worktrees](https://learn.chatgpt.com/docs/environments/git-worktrees)、[Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents) |
| Codex | 沙箱、审批与网络控制属于明确的运行边界 | “可以运行命令”应与“允许访问哪些资源”分开。[官方权限与安全](https://learn.chatgpt.com/docs/agent-approvals-security) |
| Claude Code | 读代码、改文件、运行命令、Git 交付，以及指令、Skills、Hooks、MCP | 优先打通一个会话完成开发任务的流程。[官方概览](https://code.claude.com/docs/en/overview) |
| Claude Code | 会话与工具编辑的检查点，可恢复代码或对话；不覆盖所有 shell 或子代理改动 | 回滚范围必须解释清楚，不能把备份日志当成一键恢复。[Checkpointing](https://code.claude.com/docs/en/checkpointing) |
| Claude Code | Agent Teams 有共享任务和成员通信；官方仍标为实验功能且默认关闭 | 可借鉴协作模型，但不能把实验团队当成无缺陷的成熟标杆。[Agent Teams](https://code.claude.com/docs/en/agent-teams) |
| 开源 DSH | 对话能调用项目工具、委派任务、维护计划并按权限策略审批 | Rust 主入口应保留用户原有的开发能力。[官方快速开始](https://deepseek-harness.github.io/deepseek-harness/en/guide/quickstart) |
| 开源 DSH | 三类模型协议、模型能力配置；独立项目记录、上下文压缩、持久终端和 Skills | 借鉴可扩展边界与迁移清单，避免只迁移模型请求。[模型配置](https://deepseek-harness.github.io/deepseek-harness/en/guide/providers)、[架构](https://deepseek-harness.github.io/deepseek-harness/en/reference/) |

以上是功能标杆，不是三款产品的速度、可靠性或模型效果排名。本轮没有用同一真实仓库做横向性能测评。也没有证据表明它们都内置 xpeach 多 Key 池；这是 🍑sh 自己要做好并验收的产品特色。

## 3. 当前资产：哪些已经有

| 能力 | 当前状态 | 不能误解为 |
|---|---|---|
| 对话 | 文本输入、流式回答、续聊、从历史重开；已有真实两轮验收 | 已能在对话中直接完成编码 |
| 多 Key / 多模型 | 每成员固定路由、独立 Key、总并发与相同 Key/端点的共享并发限制 | 已有自动 Key 池、故障切换、成本优化 |
| 团队任务 | 手工成员列表、职责、前置依赖、结果传递和可选汇总 | 主代理自动组队、成员讨论、自动返工 |
| 项目工具 | 列目录、读文件、按范围写文件、可选 PowerShell 命令 | 完整 IDE、代码搜索、补丁审阅或安全命令沙箱 |
| 任务恢复 | SQLite、事件回放、停止、重启标中断、手动继续 | 所有副作用都可安全重试或完整回滚 |
| 账号余额 | New API 账号验证、余额、已用额度与手动刷新 | 任务计费、每 Key 账单、预算控制 |
| WASM | JSON 输入输出的预装插件、哈希校验、fuel 和线性内存上限 | 原 DSH 插件兼容层、MCP、完整资源隔离或前端 WASM |
| 运行分发 | Windows EXE 和启动脚本；无需 Node 启动主服务 | 无任何外部依赖：命令工具仍依赖 pwsh.exe |

准确的架构描述是“Rust 服务和执行核心 + HTML/CSS/JavaScript Web UI + 受限 WASM 工具扩展”。当前没有把前端编译为 WASM，也没有让原有 TypeScript 插件自动成为 WASM 插件。

### D. xpeach、多模型、多 Key 和余额

| ID | 优先级 / 现状 | 缺少的功能 | 完成的判断标准 |
|---|---|---|---|
| F21 | P1 / 部分 | Provider、凭据、模型目录分离；多协议；推理强度、工具/视觉能力、上下文上限和兼容参数 | xpeach 实际提供的模型按真实协议运行；一个 Key 可复用多模型；不能把所有模型都强制成相同参数的 Chat Completions |

| F23 | P1 / 部分 | 单次请求/成员/团队用量面板、成本估算、预算上限、余额缓存/告警、解绑与失效提示 | 显示上游实际返回的用量；未知价格不编造金额；账户余额、Key 额度、任务成本明确区分 |

源码证据：provider.rs:168 构造固定 Chat Completions 请求，Route 没有协议和模型能力字段。engine.rs 已累计三个 token 字段，但界面未消费 usage，没有定价或预算策略。当前账号配置只有一组；余额手动查询已存在。连通检查还依赖 /models 成功，缺少“模型发现不可用但推理可用”的友好降级。能力配置可参考 [DSH 模型配置](https://deepseek-harness.github.io/deepseek-harness/en/guide/providers)，但 xpeach 的实际协议、模型和价格必须另行实测，不能从模型名称推断。

源码证据：engine.rs:139 明确禁止一个多成员任务带命令权限，因此现有 Team 不能在同一批次让成员跑编译/测试。调度是提交时已知的依赖图，工具目录没有 spawn/send/wait；最终汇总默认 tools=false。成员可以读写分配范围的文件、接收前置结果，这是可保留的基础。应先引入工作区隔离，再放开团队命令，不应仅删掉冲突校验。参考：[Codex 子代理](https://learn.chatgpt.com/docs/agent-configuration/subagents)、[Claude 实验团队](https://code.claude.com/docs/en/agent-teams)、[DSH 子代理](https://deepseek-harness.github.io/deepseek-harness/en/reference/subsystems/subagent)。

| F37 | P2 / 部分 | 键盘可达性、窄屏、长历史性能、主题/字号和本地化一致性 | 不同屏幕能完成主要流程；长回复和滚动不明显卡顿；按需改进，不等同于必须换前端技术 |
| F38 | P3 / 缺失 | 可选远程控制、多用户、组织权限和共享审计 | 仅在明确需要团队部署后设计认证、租户隔离和访问审计；本机版不为追齐功能提前复杂化 |

源码证据：server.rs 目前只暴露设置、路由、账号、运行组、续聊、取消、WASM 等接口；没有上述会话管理、Git、MCP 或插件管理接口。main.rs CLI 只有启动路径/端口与 check。旧版 initial_settings 只导入部分路由及账号配置，并且每个旧 provider 只取第一个模型，不迁移会话。secrets.rs 的持久密钥依赖 Windows DPAPI。生态参考：[Claude MCP](https://code.claude.com/docs/en/mcp)、[DSH Skills](https://deepseek-harness.github.io/deepseek-harness/en/reference/subsystems/skills)。

## 5. 不应混进“未来功能”的现有缺陷

下列六项来自此前实际复现，它们是修复工作，不是可无限延后的产品愿望。本轮已修复并纳入默认测试的项目标为“已修复”；尚未完成的仍保留在待办中：

1. A03：模型路由 ID 可命中账号令牌的同一存储空间。**已修复**：路由凭据使用 `route::<id>` 命名空间，并禁止保留账号 ID。
2. A05：更换 New API 站点且令牌留空，可能把原令牌发向新站点。**已修复**：站点或用户变化时必须重新填写令牌，并有单元测试。
3. A01：同一幂等键配不同请求体，静默复用旧任务。**已修复**：保存请求哈希，不同请求明确报冲突。
4. A02：任务与幂等映射分两次提交，失败可留下孤立任务。**已修复**：任务和幂等绑定使用同一 SQLite 事务。
5. A04：WASM table 资源缺少宿主限额，线性内存限制不是总资源保证。**已修复**：增加 table、memory、instance、table 数量限制。
6. UI01：移除中间队员再新增，默认名称可能重复。**已修复**：使用会话级单调序号生成默认成员名。

详见 [已有复现和证据](ASSESSMENT-LIVE-2026-09-20.md)。

本轮另确认对话界面的产品缺口（源码检查；没有新增付费复现）：

- 没有停止按钮；task.error 和 task.status 没有在对话内容区呈现。模型调用失败可能缺少明确反馈。
- 输入在提交成功前清空；提交失败没有还原草稿。
- 已有对话里路由选择仍可编辑，但 resume 请求只有 message，实际模型保持旧快照。应锁定选择器并解释，或实现显式换模型/分支。
- 创建对话没有刷新左侧历史；新记录要等其他刷新路径才出现。
- 每次续聊都从头连接 SSE，缺少按当前轮和事件游标隔离显示的逻辑；旧 delta 混入临时回复的风险需要故障/慢流复现。
- 会话类型靠成员名称等于 chat-session 判断；普通团队成员使用同名也会触发对话入口。应有独立 session.kind 字段。

这些应与 F01/F02 一起完成，不宜继续把“补了输入框”描述为对话产品完整交付。

## 6. 推荐产品结构与技术取舍

建议主流程为：选择项目 → 对话提出目标 → 规划/执行 → 查看工具与终端 → 审阅变更和测试 → 提交或恢复。Team 是同一会话下的可选协作视图，普通用户无需从对话复制需求到另一张成员表。

建议形成独立的 Project、Session、Turn、Agent、Provider、Credential、Model、ToolRun、Artifact、Approval 和 Checkpoint 数据边界。特别是 Session 与一次 Run、稳定 Agent 身份与成员显示名、Provider 与 Key/模型，都不应继续混为一体。这样才可以可靠实现消息重连、模型变更记录、成员续聊和成本归属。

保留 Rust 核心、SQLite、固定成员身份、依赖图和受控文件工具。WASM 适合纯计算和受限扩展；系统进程、Git、浏览器、MCP 网络连接由具备明确权限的宿主接口负责。是否把更多 UI 改为 WASM，应根据性能和开发维护收益决定，而不是作为功能完成的标志。

无需第一版就实现远程 SaaS、企业 SSO、移动原生客户端、全功能 IDE、插件商城、向量数据库或默认多代理。先提供好用的代码搜索、可靠的单会话编码流程与明确的交付证据。异构团队按任务需要开启，不能把多 Key 视为更多 Key 就一定更快或更便宜。

## 7. 三轮产品化计划与验收

| 轮次 | 交付目标 | 主要工作 | 放行条件 |
|---|---|---|---|
| 第一轮：日常可用 | 一个用户在一个真实项目里完成修复 | 修六项缺陷；统一开发对话；项目入口；失败/停止/草稿；搜索/补丁；长命令；基本 diff 和恢复；发布验收 | 新用户不手改配置，完成“连接模型—修一个 bug—运行超过 30 秒的测试—审阅改动—恢复或接受”；异常路径不丢任务/输入，不重复执行副作用 |
| 第二轮：连续开发 | 长会话、多模型和生态稳定 | 压缩/规则/历史管理；协议能力；Key 健康和预算；Git 交付；MCP/Skills 最小闭环；旧历史迁移和备份；安装升级 | 多轮开发、模型限流、重启、旧历史迁入可验证；一次真实 xpeach 小任务记录模型/Key 路由与用量，费用未知时如实显示 |
| 第三轮：团队交付 | 异构 Agent Team 真正协同编码 | 主代理拆分和跟进；成员消息；工作树隔离；独立验证和合并；可视化团队状态；测试门槛与失败返工 | 两个不同模型和两个独立 Key 实际并行完成子任务，各自测试，主代理审阅合并；制造一个成员失败后可选择性恢复，身份/上下文/成本归属正确 |

不先承诺按几天完成；权限隔离、会话模型升级与旧数据迁移需要分别估算。每轮以用户流程和故障验收放行，不按代码行数、语言占比或“测试全绿”单独放行。

最终可用性的最小演练：安装 → 配 Key → 打开真实仓库 → 对话修复 → 必要权限 → 长测试 → diff → 提交/恢复 → 重启继续 → 预算和错误可见。当前只能覆盖这条流程的部分环节，这就是接下来应补的产品工作。
