## 1. 产品定位

### 1.1 一句话目标

🍑sh 是一个 **Windows 本地优先的 AI 编程工作台**：用户打开一个项目，在同一个持久会话中提出目标，选择单模型或多模型协作，经过明确的权限审批，让 Agent 读取、修改、测试和审阅代码，最后接受、恢复或交付变更。

🍑sh 的核心差异是：

1. **xpeach 多 Key / 多模型路由**：不同成员可以使用不同 Key 和模型；系统根据并发、健康、预算和任务类型选择路由。
2. **可审阅的开发闭环**：对话只是入口，最终产物必须是可查看的文件变更、测试证据和可交付结果。
3. **本地权限和数据边界**：项目文件、命令、凭据和扩展由 Rust 主机控制；前端不能自行决定工作目录或拿到 Key。
4. **可选的异构 Agent Team**：普通任务只需要一个 Agent；复杂任务再由 Lead 规划并派生成员，不强迫用户使用 Team。

### 1.2 当前定位

当前 Rust 0.2.0 是“核心链路可运行的开发预览版”，不是稳定发行版：

- 已有：Rust 服务、流式模型调用、手工 Team/Swarm、文件读写、搜索、命令执行、停止/继续、SQLite 事件持久化、WASM JSON 扩展、New API 余额查询。
- 尚未完整：统一开发对话、项目选择、精确补丁、逐行 diff/接受、持久终端、按工具审批、Git/worktree、MCP/Skills、自动组队、迁移向导、完整 E2E 验收。
- 3080/Node 旧版只能作为迁移和回退路径，不能被当成 Rust 主产品功能。

### 1.3 产品边界

**第一阶段必须解决：**

- 一个用户、一个 Windows 主机、多个本地项目。
- OpenAI Chat Completions 兼容的模型和 xpeach 路由。
- 读代码、改代码、跑测试、查看 diff、恢复或交付。
- 任务在刷新、断网、重启后有明确状态。
- Key、New API 账号令牌、项目文件彼此隔离。

**明确不作为第一阶段前置条件：**

- 多用户云端协作、远程执行和组织租户。
- 完整复制 DSH、Codex 或 Claude Code 的所有私有实现。
- 为了“先进”而把数据库、进程、凭据和网络全部放进 WASM。
- 在没有预算、取消和结果契约的情况下无限增加并发 Agent。
- 自动提交、自动推送或自动重试具有副作用的操作。

| 模型 | `provider.rs` | OpenAI Chat Completions、SSE、模型发现、连通检查、余额 |

### 2.2 已经具备但不能高估的能力

- “Team 可运行”不等于“自动协作完成”。当前主要是用户手工填写成员、职责、依赖和路由。
- “有文件恢复接口”不等于“所有修改都可回滚”。当前 shell、外部进程和用户手动修改不属于自动恢复范围。
- “有多 Key 并发”不等于“有健康池和成本优化”。目前还需要 429 冷却、失效停用、预算和用量归属。
- “有 WASM”不等于“兼容 DSH 插件”。当前只有受限 JSON 扩展 ABI。
- “单元测试全绿”不等于“产品流程通过”。发布必须包含真实浏览器、故障路径和人工审阅。

## 3. 目标逻辑模型

产品状态不应再把“一次 Run”当作全部对象。建议采用下面的关系：

```
Project
  └── Session
        ├── Mode: Agent | Plan | Goal
        ├── Policy / Rules / Memory
        ├── Agent (Lead or member)
        │     └── Work / Run
        │           ├── Task
        │           ├── ToolCall
        │           ├── Artifact / Diff / TestResult
        │           └── Event
        └── Checkpoint
```

### 3.1 Project

项目是工作目录和规则的稳定边界，至少包含：

- canonical workspace path；
- 项目显示名；
- 项目级模型默认值和 Key 选择策略；
- 工具权限和可信状态；
- 项目规则文件、Skills/MCP 配置；
- 最近会话、备份和 Git 状态。

不同项目不能共享隐式当前目录、规则或记忆。API 请求必须携带项目/会话上下文，不能依赖全局单一 workspace。

### 3.2 Session

会话是用户看到的连续对话：

- 保存消息、模型快照、模式、权限审批和事件游标；
- 支持刷新、重启后继续；
- 一次会话可以先 Plan，再切换 Agent 执行，再回到审阅；
- 分支会话复制上下文快照，但不覆盖原会话；
- 消息、工具输出、错误和用户草稿分开存储。

### 3.3 Agent 与 Team

Agent 是一个有稳定身份的执行主体：

- `agent_id` 是不可变 ID；
- `display_name`、`role`、`route_id`、模型和推理档位是独立字段；
- 身份不由 prompt 文本或 UI 名称推断；
- 每个成员都有收件箱、输出、权限、成本和状态。

Team 是 Agent 的编排关系，不是新的凭据或会话类型：

- Lead 负责目标澄清、计划、派工、回收和最终审阅；
- 成员负责结构化工作项；
- 成员之间的消息必须有发送者、接收者、序号和持久化状态；
- 不允许使用“没有团队工具却声称已经通知成员”的提示词行为；
- 失败重派必须生成新尝试并保留原尝试的副作用记录。

### 3.4 Work / Run / Task

建议统一语义：

- **Work**：用户可见的一个目标，例如“修复登录超时”。
- **Run**：Work 的一次执行尝试，可停止、失败后继续或重跑。
- **Task**：Run 中由一个 Agent 负责的可验证工作项。
- **ToolCall**：一次文件、命令、模型、MCP 或 WASM 调用。
- **Artifact**：diff、测试结果、报告、构建产物等可交付证据。

当前 `Run.kind=chat/team` 可以保留兼容字段，但新逻辑应逐步使用 Session/Work/Task 关系，避免靠名称决定页面。

### 3.5 Route、Credential、Account

三者必须完全分离：

- **Provider**：例如 xpeach、New API、其他 OpenAI 兼容端点。
- **Route**：一个可选模型和参数的调用入口，包含 base URL、model、协议能力、并发和健康状态。
- **Credential**：Route 使用的模型 Key，绑定 route、站点和用途。
- **Account**：New API 登录账号令牌，只用于余额/账号查询，不得被模型路由读取。
- **Usage/Budget**：请求、成员、Work、账号的 token、费用估算和预算状态。

保存和读取时使用 typed namespace，例如 `route::<route_id>` 与 `account::<account_id>`，禁止以裸 ID 作为凭据键。

## 4. 目标架构

### 4.1 分层

```
[Leptos CSR/WASM UI；迁移期保留 legacy Web UI]
        │ 受校验的命令和事件投影
[Session API + Auth/Origin + DTO]
        │
[Application Services]
  Session · Plan · Review · Recovery · Project · Account
        │
[Orchestrator]
  Agent loop · Team graph · mailbox · budget · cancellation
        │
[Policy Host]
  file search/read/patch · terminal/process · browser · MCP · WASM
        │
[Provider Gateway]
  protocol adapter · model capability · key pool · health/rate limit
        │
[Persistence]
  SQLite WAL · migrations · event log · checkpoints · diagnostics
        │
[OS boundary]
  Windows DPAPI · process tree · filesystem · network
```

### 4.2 Rust 主机的责任

Rust 是可信主机和产品边界，负责：

- 项目路径 canonicalization 与目录权限；
- 文件读取、精确补丁、冲突检查和 diff；
- 命令审批、进程树、超时、输出和取消；
- Provider/Key 路由、限流、故障分类、用量；
- SQLite 事务、事件游标、迁移和恢复；
- DPAPI 凭据；
- WASM、MCP、Skills 的注册和权限授予；
- 统一错误码、诊断和审计。

### 4.3 UI 的责任

目标 Leptos CSR/WASM UI（以及迁移期网页）只做：

- 展示 Session、任务、工具状态、diff、审批和错误；
- 发送用户明确操作；
- 保留输入草稿；
- 不拼接工作目录、不读取 Key、不绕过审批；
- 不根据成员名称猜测 Team 类型；
- 所有状态来自 API/事件，不以本地变量作为事实来源。

### 4.4 扩展边界

扩展按能力分级：

1. 内置只读工具：列目录、搜索、读取、Git 状态。
2. 需审批工具：写文件、补丁、终端、网络、浏览器。
3. 受限 WASM：无 import 的 JSON ABI；后续通过版本化 capability 只读授予。
4. MCP：服务注册、工具发现、认证和每工具权限。
5. Skills/Hooks：项目/用户作用域、显式调用、超时和失败审计。

不能把 npm/TS 插件直接标为 WASM 兼容，也不能给扩展隐式注入 Key、文件句柄、网络客户端或任意进程能力。

## 5. 用户主流程

### 5.1 日常单 Agent 流程（P0 放行流程）

```
安装/启动
  → 选择或创建 Project
  → 配置模型 Route 和 Key
  → 新建 Session
  → 输入目标
  → Agent 读取/搜索代码
  → 请求写入/命令权限
  → 生成 Patch
  → 用户查看 Diff 并接受/恢复
  → 运行测试/构建
  → 查看证据
  → Git 提交或导出
  → 刷新/重启后继续
```

验收要求：

- 用户不用编辑 YAML 或手动复制 prompt；
- 工具调用、权限、文件变更和测试结果都可见；
- 失败时输入、错误和会话仍可恢复；
- 长测试超过 30 秒仍能查看增量日志；
- 接受/恢复边界明确，shell 外部修改不能被假装可回滚。

### 5.2 Plan → Agent → Review

- **Plan**：只读分析、列出文件和风险，不写文件、不运行有副作用命令。
- **Agent**：在批准的权限内执行工作。
- **Review**：展示 diff、测试、审阅意见和未解决风险。
- **Goal**：保存验收标准和完成条件，驱动长任务，不等于无限自动运行。

### 5.3 Team 流程（P1）

```
用户 Goal
  → Lead 澄清问题
  → 生成可审阅 Plan
  → 选择成员 / 模型 / Key / 预算
  → 用户确认计划与工作区模式
  → 创建互不冲突的 Work Items
  → 并行或按依赖执行
  → 成员回传结构化 Artifact
  → Lead 审阅和请求返工
  → 合并 worktree / patch
  → 独立测试
  → 最终交付
```

最低团队验收：

- 两个不同模型、两个不同 Key 的真实任务并行；
- 成员身份在第二轮消息、重启和失败重派后不漂移；
- 发生 `TEAM_NOT_MEMBER` 类错误时有明确错误，不伪造成功；
- 成员各自测试，Lead 的汇总引用工具证据；
- 共享文件有锁或 worktree，不允许静默覆盖；
- 成本、状态、失败原因和取消操作可追溯。

## 6. 目标与优先级

### P0：真正可用的单项目开发闭环

| 目标 | 交付物 | 放行标准 |
| --- | --- | --- |
| P0-1 统一 Session/Project | 项目选择、会话新建/恢复、项目独立配置 | 两个项目切换不串目录、规则或历史 |
| P0-2 文件修改安全 | search/glob、分段读、精确 patch、基于版本的冲突检查 | 修改少量行不覆盖用户新改；拒绝冲突并显示上下文 |
| P0-3 Diff/Checkpoint | 逐行 diff、接受/拒绝、检查点、恢复 | 用户能逐文件查看和恢复；边界写清楚 |
| P0-4 长终端 | 持久会话、增量日志、后台进程、树状取消 | 运行超过 30 秒的测试；刷新后可继续；无孤儿进程 |
| P0-5 审批和诊断 | 工具/路径/网络权限、审批记录、统一错误码 | 开启命令不等于开放整个磁盘；拒绝原因可理解 |
| P0-6 对话体验 | Markdown、代码复制、文件链接、停止、重试、草稿和事件重连 | 输入不丢、旧 delta 不混入、新会话可从历史打开 |
| P0-7 数据可靠性 | 事务、幂等、迁移、备份和恢复演练 | 重复提交不重复执行；异常无孤立 queued 任务 |
| P0-8 发布验收 | Windows 全新目录安装、健康检查、真实浏览器流程 | 完成“修 bug→长测试→diff→恢复/接受→重启继续” |

### P1：连续开发和异构 Agent Team

| 目标 | 交付物 | 放行标准 |
| --- | --- | --- |
| P1-1 上下文和规则 | token 预算、压缩、项目指令、记忆、计划 | 长会话不靠用户新建任务；压缩保留约束和工具配对 |
| P1-2 Provider/Key 池 | 协议能力、健康、429 冷却、失效停用、预算、用量 | 不可用 Key 不反复重试；成本归属可见 |

| P1-4 隔离交付 | worktree、patch 合并、冲突和独立测试 | 两个成员可并行开发并形成可审阅合并结果 |
| P1-5 生态迁移 | MCP、Skills、Hooks、CLI/JSON API、旧会话迁移 | 扩展复用 Rust 权限；迁移报告可解释 |

## 7. 迭代门槛和测试策略

### 7.1 四类测试必须分开

1. **单元/集成测试**：域模型、迁移、路由、事件、WASM ABI。
2. **故障注入测试**：重复提交、冲突、断网、取消、进程崩溃、错误凭据、Key 串用。
3. **真实提供方测试**：手动、隔离 Key、小任务、脱敏记录；不进入默认 CI。
4. **产品 E2E**：从全新目录、浏览器和真实项目走完整流程。

“Rust 测试通过”只能说明第一类通过，不能代替后面三类。

### 7.2 每轮放行清单

- API schema 和数据库迁移有版本号；
- 新增功能有失败路径和取消路径；
- 所有副作用动作说明重试语义；
- UI 使用事件和服务端状态，不依赖名称猜测；
- Key、账号令牌、消息、日志和诊断包脱敏；
- 启动、停止、崩溃恢复和单实例锁可重复验证；
- 当前版本、schema、EXE hash、测试结果写入发布报告。

## 8. 已确认决策与后续设计边界

用户已确认 Windows 优先的本机单用户、shared/worktree 自选、Rust 核心 + WASM UI、读自动允许而写入/命令/网络逐次审批、Lead 计划确认后派工、健康 Key 选择/冷却/任务预算。框架采用 Leptos CSR，先落地共享协议，随后逐页迁移；保留 legacy 回退直到完整流程通过。
