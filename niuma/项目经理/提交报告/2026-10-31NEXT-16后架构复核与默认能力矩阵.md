# NEXT-16 后架构复核与默认能力矩阵

日期：2026-10-31。更新人：当前项目经理。响应用户“审视整个项目，对架构和内容进行评判，是否需要推翻重来”。本轮为管理审查，没有新的产品实现派发。

## 判断

不建议整体推翻。应保留 Rust Host、持久事务、权限准入、事件和恢复机制，实质重构应用编排、兼容模型和插件装配边界；正式 Desktop 需要建设，不能按现有骨架估作接近交付。

这不是维持现状的批准。若继续把新能力叠加到 Engine、用局部验收代替产品验收、让多处历史“当前状态”共同充当导航，维护和交付风险会继续增加。当前证据支持有限迁移，并未证明原语言、数据库或 Host 权威边界选错。

## 按风险排序的发现

### A1 高：应用编排仍集中于 Engine

[engine.rs](../../../NoManCode/rust-app/src/engine.rs) 的 `run_task` 从依赖等待开始，继续处理凭据/并发槽、状态保存、遗留工具对账、上下文与工具定义、Provider 准入/调用/结算、消息落库、工具审批执行。同一类型还承担项目配置、插件管理、恢复和 checkpoint 等入口。

问题在于策略、事务协调和副作用执行的共同修改面，不在文件长度。ProviderRuntime 已抽出一段真实绑定，但并未解决整体应用结构。新增 Agent 策略或 Team 行为仍容易涉及同一协调中心。

建议保留 Engine 作为外观，逐步形成有类型的应用命令和执行协调服务。chat-agent 的下一步建议可以成为受限策略服务；身份、上下文权限裁剪、网络与工具准入、持久提交和恢复裁决继续由 Host 负责。验收必须证明替换策略实际改变行为且不能绕过这些守门，不能只将方法搬到另一个文件。

### A2 高：新旧模型尚未形成清晰的长期边界

[domain.rs](../../../NoManCode/rust-app/src/domain.rs) 同时保留 Task/Run 与 Session/Turn/TurnTask；后者以 `legacy_run_id`、`legacy_task_id` 关联执行记录。[store.rs](../../../NoManCode/rust-app/src/store.rs) 的 `save_task_tx` 同事务更新旧任务和新投影，Engine 仍以 Task 执行。

这些事务校验值得保留，当前不能据此断言双写已经漂移。但后续能力必须同时理解两套表达。应先写清每个状态的唯一权威、投影规则与兼容适配边界，再收敛调用者；不能一次删旧表或在迁移时重建全部状态机。

NEXT-16 两次 resume 分类/文案回归已修复，仍提供一个具体教训：[server.rs](../../../NoManCode/rust-app/src/server.rs) 通过 `anyhow` 下转识别 Store/Checkpoint 的业务错误，传输层容易遗漏新原因或改变旧响应。应用错误类型和传输映射应明确归属，原响应兼容测试继续约束重构。

### A3 高（相对于项目书承诺）：插件化只有部分生产能力闭合

Files、Shell、Completion 都有真实生产绑定，不能称插件系统只是空壳。但 Files/Shell/Provider 各自持有 PluginHost；[plugin_management.rs](../../../NoManCode/rust-app/src/plugin_management.rs) 的持久公开管理仅接受 `builtin.files` 和 `builtin.shell`；Provider 只有进程内 Rust 控制，重启默认重新启用。其请求体还须与 Host 当前 Completion 协议完全相等，不能把这个局部 codec 替换点宣传成任意协议 Provider 的通用接入。

[plugin_host.rs](../../../NoManCode/rust-app/src/plugin_host.rs) 对 WASM/process 声明明确拒绝执行。可信内置 Rust 的接口约束也不是恶意第三方代码隔离。

需要完成默认组合的真实依赖、生命周期和替换验收。不能仅添加 manifest 名称，也不能将尚未完成的插件目标改称 Host 能力后宣布完成。下表区分安全权威与可替换面，未替项目书取消要求。

### A4 高（相对于 Desktop 交付）：正式界面仍需实质建设

[Leptos App](../../../NoManCode/rust-app/crates/ui/src/lib.rs) 当前只渲染标题、技术说明和会话类型。WASM 编译通过证明可编译，不能证明项目选择、聊天、审批、Diff、恢复与重连的交互已经可用。旧 fallback 的存在也不等于阶段二完成。

目前合理定位是“具有已验收 CLI 开发链路的后端工作台，完整产品建设中”。正式前端可以按 Host 协议重新组织和实现；这不要求重写后端。

### A5 中：文档的当前状态仍失真，产品范围缺少简洁收口入口

[CLI 使用说明](../../../NoManCode/docs/cli-first-release-acceptance.md) 首段与 NEXT-16 节仍写组合待验收，而当前主线已经整合最终受测代码。这是本轮可直接核对的文档缺陷。经理启动说明、人员入口和身份历史段也含多个旧“最新”，依赖接手者自行判定优先级。

项目书的长期方向有价值，但目标、历史快照、人员安排与旧下一步混排。建议当前导航只维护唯一状态；每阶段维护要求、实际入口、验收证据、剩余项的短矩阵，历史原件按轮次保留。完整 Team、MCP、Skills 等保持范围，只调整交付顺序；局部排除项不得永久删除目标。

## 13 项默认能力：当前事实与剩余工作

以下路径以 `NoManCode/rust-app/src/` 为基准。Host 权威是不可绕过的最终控制，不意味着相关算法、策略、适配器都不可替换，也不意味着默认插件目标已完成。

| 默认能力 | 当前生产接线 | 必须保留的 Host 权威 | 剩余组合/替换缺口 |
| --- | --- | --- | --- |
| core | main 初始化 Store/恢复/Engine；Host 管理生命周期 | 身份、事务、权限与生命周期控制 | 明确根组件的版本化接口与装配依赖；不能用整块 Engine 代替清晰内核 |
| session-log | Store/Repository 权威日志、server 事件流 | 同事务状态/事件、顺序与游标 | 尚无独立生产插件绑定；如增加投影/导出，提交后消费、可续读去重，不建立第二权威日志 |
| local-project | project_config、Engine/Store 项目操作 | 稳定项目 ID、配置版本、根身份及授权 | 项目发现等可替换面及装配仍需设计，不能直接把 CRUD 更名为插件 |
| workspace | workspace 身份/路径检查；文件操作经 ToolRuntime | 根与路径边界、身份重验、变更准入 | 根组件与操作适配器的契约仍需收敛；不是 OS 沙箱 |
| provider-xpeach | Completion 经 ProviderRuntime；Agent 与 route check 均消费；Models/Balance 保留旧路径 | 凭据、目标、网络/预算 claim 与结算 | 公开持久管理、其他 Provider 操作与跨组装配未完成；当前 codec 非任意协议适配 |
| file-read-search | builtin.files 提供 read/list/search，真实 consumer/lease | 项目与任务权限、路径校验 | 与 write 共用同组，不能独立启停；完整默认组合依赖验收仍缺 |
| approval-policy | Engine 调用 approval 判断、Store 记录决定与 claim | 最终授权、逐次审批、单次消费 | 策略建议服务尚未绑定；任何替换都不能自授权限 |
| file-write | builtin.files 的 write 服务；Host 审批及变更账本 | 写前 claim、前后像、结果及 unknown | 非独立插件；停用不撤销已发生写入，与恢复链共同验收 |
| shell | builtin.shell 独立服务组与持久管理 | 审批、命令/网络告知、执行回执 | 不是 OS 隔离，不承诺任意外部效果回滚；默认组合中的失败/卸载语义仍须整体证明 |
| git-diff | Engine 调用 git_diff | 根校验、有界执行、事实归属 | 尚未通过插件服务装配；只读算法/展示替换须消费同一变更事实 |
| checkpoint-restore | Engine/Store/checkpoint 实际执行 | claim、封存、冲突/partial/unknown、受限文件恢复 | 可扩策略/展示边界尚未冻结；不能把安全恢复事务任意卸载 |
| recovery | 启动 Store recover、执行与恢复回执 | 不伪造成功、不自动重做未知副作用 | 插件恢复钩子、诊断建议与 Host 裁决的组合仍缺契约 |
| chat-agent | Engine 内联轮次循环，调用真实 Provider/ToolRuntime | 上下文权限、准入、落库和终态裁决 | 生产可替换策略服务尚未实现，是应用边界重构的重点候选 |

## 保留、重构、建设与下一步

| 范围 | 处置 |
| --- | --- |
| Host/SQLite/协议事件/安全与恢复基础 | 保留；用已有事务、迁移和故障用例约束演进 |
| Engine 编排与业务错误边界 | 分步骤实质重构，建立可观察的策略替换和有类型的应用结果 |
| Task/Run 兼容 | 明确权威与适配，迁移验证后再考虑退出；不先删库表 |
| 插件装配 | 补真实生产依赖、可替换面、公开管理与生命周期验收，不按名字数量结项 |
| Leptos/Desktop | 按公开 Host 协议建设用户流程与浏览器 E2E |
| 当前文档 | 修正失真状态并收敛导航，保留历史原件 |

建议下一项内核契约优先解决 chat-agent 与 Host 执行协调边界：先明确受限输入、候选动作、取消/重放、类型化失败及 Host 不变量，再登记唯一所有权、新基线和隔离树。不同时迁移数据库、替换线程模型、重写 Provider 协议和建设全套第三方沙箱。该方向仍需形成可执行契约，本文不是 NEXT-17 派发。

交付顺序为：真实应用边界试点和默认能力组合收口；同步修正使用说明；完成阶段一剩余逐项验收及可复现交付；正式 Desktop；按项目书依赖推进 Team、MCP、Skills、上下文和 KeyPool。现有完整空库 CLI 故事作为持续回归，付费实机、发布物、性能及浏览器验证分别记账，不互相替代。

只有当核心状态模型无法满足必要不变量、局部迁移不可闭合，或替代原型通过相同历史数据/安全/故障验收并证明迁移可行，才扩大重写范围。当前没有这些证据。架构审查完成不等于完整项目完成，长期目标保持 active。
