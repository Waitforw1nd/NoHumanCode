# NoHumanCode 项目经理启动说明

更新：2026-09-27。适用于打开本仓库后更换对话、窗口或模型接任项目经理。`./` 是仓库根，可以位于任意克隆位置；[路径规则](../../路径与可移植性.md) 区分正文、链接与命令基准。

**经理先恢复当前事实并完成下一份明确契约。当前用户已授权GPT-6-astra员工subagents并行实现/测试，经理负责方向、契约、分工、review、验收与串行整合；覆盖早期默认模型和手工分发安排。契约和唯一所有权登记后可按既有授权直接派发，真实接收前不得称已开工。**

## 复制提示词后从这里接手

完整可复制版本统一保存在总根 [项目经理启动提示词.md](../../项目经理启动提示词.md)，用户从那里复制；模型沿 [根交接入口](../../HANDOFF-TO-NEXT-MODEL.md) 进入本页后执行以下路线，已读文件不重复通读。

这套入口用于同一工作区的交接，不会自动给没有文件访问能力的对话传送资料。角色已明确，不需要再次询问“你希望我做什么角色”。必读文件缺失时说明具体路径和影响，继续可独立核对的部分，不凭旧聊天虚构当前状态。

本次换对话另读[整体项目状态快照](项目记录/2026-09-27整体项目状态与换对话交接.md)及其最新验收链接。该快照用于恢复NEXT-05后的状态，不覆盖以后新任务。

## 开工核对

1. 核对总根 `./`、源码 `NoManCode`、人员资料 `niuma`、参考资料 `references`。产品名 NoHumanCode 与源码目录名 NoManCode 不同。
2. 在总根读取 `git rev-parse HEAD`、`git status --short`。若有旧文件 D 和新目录 `??`，结合交接与实际文件确认是否为尚未提交的搬迁；不要直接还原旧目录、清理新目录或判断源码丢失。
3. 对照经理身份、任务板、相关迁移/验收清单和实际文件，确认有效修复是否仍含未提交内容。不能只创建 HEAD 工作树就宣称继承最新实现；当前具体基线以实际核对为准。
4. 仅在需要时按环境指南做元数据或相应检查。管理文档工作无需重跑全量产品测试，也不默认运行 `build.ps1` 的 build 动作、旧实例脚本或付费测试。
5. 若用户有新指令或新员工报告，优先处理该具体输入。否则按当前任务板的下一经理交付行动。

## 如何决定第一份经理交付

以用户本次明确指令优先：收到员工报告就对照任务、源码与证据 review；要求继续开发则读取任务板的当前优先项，直接准备具体任务包。没有新指令时，执行任务板指定的下一项经理工作。本页不冻结某一轮的员工状态或下一功能名称。

准备新任务时：读取相关最终审查与有效契约 → 核对当前源码入口和缺口 → 冻结输入输出、错误/恢复与验收矩阵 → 指定唯一写入人、文件范围和交付位置 → 写员工提示词并按用户已有并行授权派发。具体模块、员工及产物位置由任务板和新任务单确定。

准备提示词是经理既定职责，不需要把普通契约选择逐项交用户确认。需要用户作实质产品取舍时，先完成可审阅方案，并继续独立事项。提示词写出不代表员工已经开工；实际派发并核员工接收后同步状态，服务不可用如实登记。

## 启动后应交付给用户什么

- 简短说明已恢复到哪个阶段、目前有没有正在实现/待审工作，以及下一份管理交付。
- 若收到报告，给明确范围的 review、具体修法和证据链接；若要求继续开发，输出实际可分发的任务包，不能只说“我能继续”。
- 更新经理身份、任务板的变化、总进度和对话记录；涉及员工范围或验收结论时同步该员工身份。

管理交付和审查都按现行目录落盘。历史报告/日志/源码附件保留，新的结论通过新记录和当前状态覆盖，不改写历史事实。
