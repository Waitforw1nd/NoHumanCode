## 用户行为与兼容裁决

1. 同一实际数据域只能有一个运行 Engine controller；正常 Host、直接库调用、恢复入口遵守相同规则。查询连接与合法多个 Store 事务连接仍可存在，不能把“多连接”一概禁用。
2. 保留当前 `--check` 可初始化空库的产品含义，但它必须持同一维护排他权才可迁移/初始化；与活 Host 冲突时明确 busy，不能修改 schema、配置或恢复状态后再失败。本任务不另加一个用户可见检查模式。内部可增加真正只读打开接口用于查询和预检。
3. 旧 `Engine::new/new_recovered` 可以明确迁移签名，或通过统一受信工厂取得真实执行权；不保留默认不校验的旁路。未显式恢复的构造也不能绕开 epoch/phase 封门。现有 builtin 工具/审批/预算/管理/聊天语义保持，不默认启用 worker。
4. 同一 owner 的引用供合法派生工作持有，不授权再次组装独立 Engine；同进程第二 controller 与跨进程第二 Host 都必须拒绝。恢复期间不可并发启动任务，运行中的 recover 不能悄悄中断活任务。

## 必须落实的内核行为

复用 C34 的 OS guard + 数据域身份 + 数据库 epoch + 单 controller 设计。先选定一种具体有限 Windows 实现并在在途短报中列出算法、支持/拒绝的路径形态和真实生命周期，然后继续代码，不另写泛化长文。

- 实际域身份不能只依赖输入路径字符串或目录旁的另一个锁文件。同库别名/大小写/相对路径要统一仲裁或明确拒绝；跨目录数据库硬链接、reparse、锁/DB 替换要可靠识别并拒绝，或确实汇聚同一个不可替换的 OS 排他资源。拒绝策略必须在有效建立执行权前生效，并覆盖持有期间身份变化。固定目录/文件句柄与 SQLite 打开对象之间的联系必须解释、验证；缺库首次创建有明确 bootstrap 顺序。不得因为方案难就放弃实际身份，只保留 canonicalize 或 process-local HashMap。
- OS guard 取得后才允许迁移/初始化；合法普通多连接须与维护权区分，不能先有副作用地调用旧 Store::open 再竞争锁。连接、能力与 epoch 绑定同一数据域，不能把别处 owner 带入另一个 Store。
- 在 IMMEDIATE 事务中登记新 epoch 与 recovering 状态；溢出、损坏、提交不确定、身份失配均封门。恢复完成并通过同事务 epoch/phase 校验，才能 active；恢复失败不发布可运行 Engine。schema 迁移保留历史数据与已有管理意图。
- 所有现有能够创建执行、副作用领取、接纳迟到结果、变更运行生命周期以及恢复的写入口，必须持不可伪造能力并在相应提交事务中验证 domain/epoch/phase。只在 Engine::start 外层检查不足。普通配置、查询、审批决定等按真实作用分类，不机械给所有 SQL 加独占；任何能重新启动未知操作的路径不能绕过 fence。报告列完整入口审计映射，明确哪些靠共同受约束的低层入口保障。
- 授予 OS 操作之前在准入门登记 in-flight，关闭门后不授新票，已授票的同步调用、异步 closure、spawn_blocking 和必要回收观察继续持 guard，直到真正结算。不能把 future Drop、epoch 变更或 main 局部变量退出当 OS 调用消失。现有 builtin 执行路径必须实际接线；为未来 W2 留同一能力接口，但本轮不修改 B 文件。
- owner 死亡与获取新锁不证明旧副作用或 worker 退出，现有 unknown 不重发语义必须保留。不得添加 force-clean 布尔开关或从用户路径接收清理证明。不能为保住 guard 无意形成永久引用环；关闭/释放和未知保留分别有可观测状态。

Windows 本机为正式验收平台。其他平台不得以无锁成功桩绕过保证；保留明确编译隔离与合理受支持行为，缺目标只记未验证，不下载工具链。

## 直接验收

固定候选交完整 SHA/产品/Rust tree、实际差异、迁移与公开调用兼容表，以及真实 guard/Store/Engine/in-flight 所有权图。以下均须有可执行测试，不以接口存在作为通过：

1. 同一进程多 Store 查询/合法事务可用；第二 Engine、运行期间第二 recover 被拒，且活任务状态未被更改。共享 owner clone 不能创建第二 controller。
2. 两个真实 Host 同域竞争只能一个执行；`--check` 遇活 Host 为 busy 且库内容/配置/schema 不变，空库检查仍按原约定成功初始化。
3. 别名、硬链接、reparse、锁/DB 替换和首次建库竞争，逐项证明统一仲裁或实际拒绝。攻击准备失败只算未覆盖，不算拒绝通过；保留普通路径成功正控。
4. 持 guard 后登记前、epoch 提交后恢复前、恢复提交前后真实强杀，下一 owner 正确取得新 epoch，未决状态保守保留。测试父方不得持待证明会释放的锁，依照现有进程夹具标准持真实 process 对象核回收。
5. 旧 epoch 迟到写入、同数据域错误阶段、跨域能力、事务失败/提交不确定均拒绝；已发出的副作用不能因 epoch 更新而自动重派。
6. 在途 OS 调用延迟及取消时 guard 保持；能够证明旧工作结束后才允许新 controller。该证明不能只检测数据库 epoch，需实际在途工作和锁竞争交错。
7. 迁移、已有 builtin CLI/审批/管理/工具结果和重启故事回归。不要把旧固定版本 837 结果冒称新 schema18 全量通过；最终整合前要有受影响测试与完整 workspace 门禁。

先集中完成静态候选；经理审后排动态，失败保留现场、unknown 停止后续进程启动。方案实现遇到确实不能同时满足的约束时，给具体代码/OS 证据和最小取舍，不静默放宽。C34 是设计依据，本任务才是正式实施授权；完整 NEXT-21 和全项目保持未完成。
