## 1. 第一轮实际完成了什么

| 层次 | 已完成的能力 | 对项目的作用 |
| --- | --- | --- |
| 领域与 SQLite 基础 | 稳定 Project/Session/Agent/Turn/Task 身份，schema 6 迁移与结构检查，新旧数据兼容，组合提交，状态/事件事务，幂等与恢复基础 | 让身份、历史和状态以持久数据为准，为执行层提供统一入口 |
| 连续 Chat 应用服务 | 已有单 Agent、无工具会话追加新消息，复用上下文和项目，新建 Turn/Task；处理重试、竞争、取消、中断及历史保护 | 后端能进行连续回合，不用把 resume 当作新消息 |
| 现有 HTTP/SSE 传输 | 结构化输入/错误、安全拒绝响应、严格游标、重连、范围隔离、流内故障与断线行为 | 让已有能力以一致、可诊断的接口和事件流对外提供 |

当前存在两条已验收链路：既有 HTTP 创建 → Engine → Store → 执行与事件读取；新增 `Engine::send_chat_turn` → 原子追加 → 后台执行。下一步要把新增消息的 HTTP 写入口接到第二条链路，并完成联合验收。

最近一次集成基线为 **99 项正式测试通过、0 失败、1 项付费 live 忽略**，fmt、Clippy、WASM 检查通过。B 的 `session_turns` 为 17 项，C 的 `http_contract` 为 11 项，均包含在 99 内。A 最终收尾时的 71 项是当时全仓基线，不是 A 独立新增 71 项；B/C 各自的 99 也不能相加。

负责人另外完成 B 的 8+2 项、C 的 7 项隔离审查探针，未计入正式 99，也不全部等同于已纳入正式回归。通过基线包含 HEAD `8f0ccdc79bf5443caf53e0bf98d455ffd9ef9da5` 之外的有效未提交修改；当前没有据此提交、发布或替换运行实例。

## 2. 三位员工的职能与责任边界

| 员工 | 核心职能 | 本轮实际工作 | 主要文件/接口 | 必须守住的边界 |
| --- | --- | --- | --- | --- |
| A | 领域契约与持久化基础 | 对象与稳定 ID、Repository、迁移、归属、幂等、新旧投影、事务与恢复基础 | domain、protocol、Store/Repository 相关区域 | 数据规则由统一入口保证，不能让调用方自行拼接规则；迁移验证真实约束 |
| B | 应用服务与执行协调 | 连续消息如何形成新轮次，何时回放/拒绝/提交/执行，如何保护历史和恢复 | Engine::send_chat_turn、Store::append_chat_turn、领域 DTO/错误、session_turns 测试 | 提交成功后才执行；回放不再次派发；检查前序与写入在同一事务内 |
| C | HTTP/SSE 接口适配 | 请求解析、错误映射、安全拒绝、事件流编码、游标与重连 | server.rs、http_contract.rs、HTTP-SSE 契约 | 不在传输层重写领域/存储规则；客户端断线不能变成业务取消 |

A 与 B 都涉及 Store/Repository，这是先后交接的职责重叠，不代表可以同时修改同一区域。当前 B 已完成应用服务扩展；以后若 A 再改共享数据层，必须由新任务单指定唯一写入人。

三位员工都负责自己范围内的编写、调试、正式测试和报告。负责人负责方向、跨模块契约、分工、审查、必要的独立复验与放行；用户负责产品取舍和分发员工提示词。员工提交报告不等于自行验收通过。

## 3. 员工 A：问题、修复与复盘

**交付过程：**有第 1.0～1.5 轮审查记录，最后由负责人按用户明确授权补齐实现和测试后放行。A 完成了对象、迁移、投影和多轮修复；不能把最终版写成“A 第 1.5 轮已独立全部完成”。

| 出现的问题 | 影响 | 最终处理 |
| --- | --- | --- |
| 新旧幂等查询、提交和 Engine 使用不同判断；旧 Run 回放丢 Task | 同 key 可能走不同语义，兼容回放不完整 | 统一 classify_both，显式区分 Turn/LegacyRun，读取完整旧 Task 并接入真实产品入口 |
| schema 只检查列名或索引名 | 同名普通索引、错误 PK/FK 等也可能被当作有效结构 | 校验类型、非空、主外键、唯一索引及列顺序；迁移和版本标记同事务 |
| canonical/legacy Task ID 冲突，曾按同一 Turn 判断“同一任务” | 不同 Task 可能被混为一体，事件归属不可靠 | 按真实 Task 行身份裁决两个候选，拒绝跨表身份碰撞并检查历史数据 |
| 事件、旧 Task、首次创建等路径的凭据处理不一致 | 已知格式的凭据材料可能进入业务持久化数据 | 统一拒绝/脱敏边界，覆盖敏感字段、已知文本格式和回读；补 Authorization 漏处理反例 |
| 依赖替换、复合创建、状态和事件没有完整原子保护 | 失败后可能留下部分状态或错误关系 | 统一组合命令与状态事务，内部 SAVEPOINT，验证失败后外层继续提交也安全 |
| 新表、枚举和接口尚未完整进入 Engine 实际调用链 | 契约存在，却不能证明真实业务使用了它 | 最终接通创建、执行状态、恢复、稳定 ID 依赖与基础 HTTP/SSE 链路 |

**本轮主要改进点：**修改一个函数后，必须检查同一规则在查询、写入、旧兼容入口和实际调用链中是否都生效。数据层测试应直接制造错误约束、身份碰撞和事务失败，不能用“表存在、名字一致”代替正确性。

**负责人需承担的部分：**A 最初任务排除了 Engine/server，后续基础放行范围扩大到真实接入。范围变化与集成责任应及时写入任务单；返工次数不能全部归因于 A 的实现能力。详细事实见 [A 复盘日志](../../员工A/复盘/员工A复盘与反思日志.md) 和 [A 最终审查](<../../员工A/审查记录/第一轮/员工A 最终审查.md>)。

## 4. 员工 B：问题、修复与复盘

**交付过程：**第 1 轮 → 第 1.1 轮 → 第 1.2 轮通过。生产实现和正式测试由 B 完成；负责人提供反例、具体修法和隔离复验，没有代改 B 的共享实现。

| 出现的问题 | 影响 | 最终处理 |
| --- | --- | --- |
| B-R1：用最后写入的事件判断最新回合（P1） | 给旧轮补事件后，历史轮可能被错误重开 | 按每个 Turn 的 MIN(seq) 判序，固定反向 ID/同秒夹具，并验证旧事件不改变 latest |
| B-R2：候选在事务外复制前序，提交时未核对（P1） | 期间完成的合法 resume 可能被漏进下一轮上下文 | 立即事务内比较真实前序的 messages、route、workspace、spec 快照，冲突明确拒绝 |
| B-R3/B-R4：畸形工具历史、多 Agent、错误 workspace 放行 | 请求超出无工具单 Agent 切片，可能错误派发或改变项目上下文 | Engine/Store 共用无工具前缀规则，在事务内核对 Agent、路径和归属；空工具数组明确允许 |
| B-R5：测试没有建立所声称的场景 | 普通成功或无关失败掩盖重启、竞争、排序等缺口 | 真实分块 mock、目标 Task delta、独立 Runtime 停止、Barrier、反向 ID、单故障夹具和真实 resume running |
| B-C1：按中文文案把读取损坏判断为不存在 | 误导调用方，后续接口可能返回错误状态码 | 用缺行/解码错误类型分类，CorruptState 保留底层原因链，其他存储错误继续传播 |

典型测试误区包括：先等待再一次性返回不算部分流；drop 外部 Harness 不等于停止持有 Arc 的后台执行器；先 await 第一笔再发第二笔不算并发入口；同时放两个错误不能证明每个守卫都有效。

**本轮主要改进点：**把“能跑通”推进为“在正确时间点验证正确任务”。测试要同时证明前置状态、目标错误、持久化结果和 Provider 调用数；独立 Store/Engine 的竞争不能只靠单个内存锁推断。

B-R1～B-R5 已全部闭合，B-C1 原反例也已闭合，见 [B 最终审查](<../../员工B/审查记录/第一轮/员工B 最终审查.md>) 和 [B 第 1.2 轮复审](<../../员工B/审查记录/第一轮/员工B review 1.2.md>)。

## 5. 员工 C：问题、修复与复盘

**交付过程：**第 1 轮 → 第 1.1 轮 → 第 1.2 轮通过。生产实现和正式测试由 C 完成；与 B 保持文件所有权分离。

| 出现的问题 | 影响 | 最终处理 |
| --- | --- | --- |
| C-R1：只识别明文 after 参数名 | 编码后的重复/非法游标可被忽略并从 0 重放 | 参数名严格解码后再识别、计数；两种 SSE 复用同一解析规则 |
| C-R2：部分存储一致性故障被当成请求 400 | 客户端无法正确识别服务端数据故障 | 已进入纯读取边界后安全兜底 500，同时保留真正的 404/409 和业务参数错误 |
| C-R3：Path 提取失败绕过统一错误体 | 非法路径得到框架默认纯文本 | 显式接收 PathRejection，统一为 JSON 400 |
| C-R4：损坏事件名使 SSE builder panic | 已开流连接直接断开，没有预期错误帧 | 构帧前校验 kind；失败只发一次 error 后结束，不越过已发游标、不写业务事件 |
| C-R5：断线、交错、未来游标和流内故障夹具不足 | 无法证明报告中的完整传输时序 | 用真实运行任务、同名但不同 ID 的交错事件、真正未来游标、同一 HTTP Response 收首帧后注入故障 |
| C-R5 收尾：notify_waiters 单次握手丢失 | Provider 先通知、测试后等待时会误报超时 | 改 notify_one 保存 permit，正式回归固定晚等待，保留断线/完成/调用数/重连断言 |

应区分实现问题与证据问题：JSON 读取故障的同流错误处理原本已能正确工作，初版 H10 没有证明它；坏 kind 引发 panic 则是另一条真实实现缺陷。最后 H7 的丢通知属于测试同步问题，不是生产断线会取消任务。

**本轮主要改进点：**接口适配要覆盖框架提取阶段、编码变体和开流后的失败；长连接测试应明确保存连接、缓冲与游标，并用可靠通知控制时间顺序。

C-R1～C-R5 已全部闭合，见 [C 最终审查](<../../员工C/审查记录/第一轮/员工C 最终审查.md>) 和 [C 第 1.2 轮复审](<../../员工C/审查记录/第一轮/员工C review 1.2.md>)。

## 6. 三位员工共同出现的问题与流程改进

| 共性 | 第一轮表现 | 后续执行要求 |
| --- | --- | --- |
| 局部修复没有覆盖完整调用链 | A 的兼容/创建入口，B 的 Engine/Store 双边界，C 的框架提取与 SSE 构帧 | 每个不变量列清所有入口，逐项核对最终真实调用路径 |
| 测试通过不等于目标场景成立 | 假 partial、无效并发、顺向 ID、多故障遮挡、开流前损坏冒充开流后故障 | 先断言前置条件成立，再断言目标结果；失败用例每次只引入目标故障 |
| 只看错误或对象数量，遗漏副作用 | 任意 is_err、只数六类实体却未覆盖事件/幂等 | 断言具体错误类型，以及本场景相关的任务、事件、幂等、活动状态和调用数 |
| 报告措辞超过证据强度 | 将计划、部分覆盖、一次通过写成完整能力 | 报告分清已实现、已验证、未验证、已批准延期，引用快照与日志 |
| 并行版本和构建环境混淆 | B 中间态影响 C 全量检查，Windows EXE 占用，PATH 找不到 pwsh | 固定审查源码及哈希，隔离输出；记录实际 shell 路径；按当时快照分配问题归属 |

负责人也有改进责任：范围扩大要同步任务单；同一问题连续两次未闭合要给具体算法、入口与反例；审查探针自身也要验证有效性；不能把非阻断补强不断升级成新返工。A 的部分历史安全推断已在复盘中更正，不把旧意见永久当成事实。

C 报告中记录的 B 死锁、嵌套 Runtime 和格式问题属于当时的并行中间态，不计为 C 的传输缺陷；后续版本通过也不意味着早期报告失实。类似地，返工轮次、测试总数不能直接用来排名员工能力，三人的任务复杂度与范围变化不同。
