## 2. 下一轮最容易踩的具体问题

| 注意点 | 正确做法 |
| --- | --- |
| `commit_turn_bundle` 用于新上下文 | 它会插入 Session；向既有 Session 追加 Turn 应复用内部提交事务，不能再次创建 Session |
| resume 与发送新消息是不同动作 | 当前 resume 复用 Task/Turn；新消息创建新 Task/Turn，保留旧轮次快照 |
| SessionId 不等于 legacy_run_id | 通过 Session 显式读取映射；`domain.rs` 中声称二者恒等的旧注释不应作为实现依据 |
| `turns_for_session` 按 `created_at,id` 排序 | 时间是秒精度，UUID 字典序不代表新旧；不要直接 `.last()` 当作最新提交回合 |
| 一份 Task.messages 已可能包含完整前缀 | 新一轮不能把所有旧 Task.messages 再拼一遍，避免上下文倍增和重复消息 |
| 幂等重试可能发生在新轮次已创建或结束之后 | 先分类并回放，再判定能否追加；回放不得受“上一轮已不是最新”误伤，也不得再次 launch |
| 已有同 key 的旧 Run 不代表可转换为 Turn | 显式拒绝不适用的新命令或按已批准兼容策略处理，不猜造领域身份 |
| 内存锁只约束该 Engine 实例 | 会话追加的“上一轮仍是最新且允许发送”条件必须与新 Turn 持久化同事务验证 |
| 全局 Settings.workspace 会变化 | 已有 Session 绑定 Project；已有会话执行使用持久化项目和任务快照，不能悄悄切换到全局新目录 |
| 模型路由与凭据需要分离 | 保存路由快照和 ID，真实 Key 由既有安全入口获取；地址不匹配时失败，不能把新 Key 发往旧地址 |
| 旧投影现在可能含多轮 Task | 不能用 `run.tasks[0]` 猜本轮任务；用 TurnTask→legacy_task_id 定位 |
| 提交成功与进程启动之间仍可能崩溃 | 重启后标为 interrupted，回放只返回原对象；不能据此宣称已经实现持久 Scheduler 或恰好一次模型执行 |

## 3. 不变量继续保持

- 任务、Agent、Turn、Session 和 Project 归属由稳定 ID 校验；新依赖不用显示名。
- 状态、新旧任务投影和事件同时提交；新增命令也要测试事件写失败回滚。
- 事件序号由数据库分配，Session SSE 只返回正确范围，不能由调用者伪造游标或挂错会话。
- 所有新业务写入经过 Store 命令；员工不得通过公开数据库连接绕过校验。
- 数据库迁移既验证旧版本升级，也验证当前版本重开；不静默忽略损坏结构。
- 凭据边界涵盖首次创建、增量保存、错误、工具数据和历史回读，不能只修某一处序列化。
