## 结论

产品目标没有被替换，第二轮完成的审批、事务、执行事实与安全恢复直接支持“可审阅、可恢复”的本机编程工作台。但已经出现需要纠正的架构整合和交付重心偏移：独立组件及局部安全契约持续收口，生产插件装配和单 Agent CLI 开发闭环仍未贯通。若继续逐项扩充横向组件而不完成真实用户流程，最终容易形成一个直接调用工具的 Engine，加上一套没有接管执行的插件框架。

这不是认定员工已验收切片失败，也不是认定所有未完成项都是偏移。局部范围验收仍有效；经理需要负责让各切片回到项目书的整体交付目标。270 项通过不能证明阶段一工作台已经完成。

依据：[项目书](../../../PROJECT-BOOK.md) §1、§3、§4、§5.1、§10；[开发守则](../../../项目开发守则.md)；[第二轮架构总结](../开发记录/第二轮整体架构总结-2026-09-26.md)。

## 按优先级列出的发现

### DIR-01 / P1：CLI 参考客户端仍停留在审批辅助入口

项目书 §5.1 要求 CLI 完成选择项目、创建 Session、对话、工具、审批、修改/测试、事件和 Diff、接受/恢复/继续；§10 也明确 create/send/status/resume 的贯通切片。

实际 [cli.rs](../../../NoManCode/rust-app/src/cli.rs) 第 12～54 行的命令集合只有 `task approvals`、`approval get/approve/deny`。没有创建/发送、任务观察、事件重连、取消、变更查看、恢复与继续的完整命令链。HTTP 上已有部分能力不等于 CLI 用户能完成该流程。

判断：单看 NEXT-04A 是有意限定范围，验收正确；结合整个阶段，完整参考客户端反复留在后续，构成交付重心偏移。应优先补现有 Host 能力的客户端贯通，不先扩 Team、MCP、Desktop 或新的插件运行形态。

关闭标准：从 CLI 进入临时项目、发起单 Agent 任务、读取代码、处理拒绝/批准、修改并运行本地测试、读取事件与变更、恢复并继续；停止再启动真实 Host 后按同一 Session 查询并继续，未知副作用不得被重试。当前缺失的 Diff 另以明确小范围接入，不能用变更路径清单冒充 Diff。

### DIR-02 / P1：插件架构已经实现，但尚未约束生产执行

项目书 §3.1～§4 要求 Host 管理 Registry/Context/生命周期，能力通过版本化边界组合、替换与撤销。

源码搜索 `PluginHost|PluginCatalog|plugin_host|plugin_catalog` 在 `src` 中只命中 [plugin_catalog.rs](../../../NoManCode/rust-app/src/plugin_catalog.rs)、[plugin_host.rs](../../../NoManCode/rust-app/src/plugin_host.rs) 及 lib 导出；没有生产 main/Engine 使用。plugin_host 文件头明确仅纯内存 builtin 生命周期，不接文件、网络、数据库或进程。与此同时 [engine.rs](../../../NoManCode/rust-app/src/engine.rs) 第 647、655、974 行仍直接调用 `workspace::definitions`、`provider::complete`、`workspace::execute`。

判断：分步落地本身合理，但目前“可组合、可替换、可撤销”主要只在独立组件内成立，尚不能证明禁用插件会撤销真实工具可用性。继续把新能力直接堆进 Engine 会扩大结构性整合债务。不能声称整个产品已经插件化；也无需为纠偏推倒已有 Engine、安全网关或一次性重写全部 Provider。

关闭标准：先用一个只读工具和一个需审批写入工具完成最小 builtin 生产装配；工具声明、查找、调用通过版本化服务边界，副作用仍由现有 Host 审批/claim 执行；禁用/卸载后新调用被拒绝，注册/监听撤销，已 claim 的在途调用有明确终结与恢复规则。禁止另建绕过现有审批的插件执行通道。WASM/process 接入排在这个证据之后。

### DIR-03 / P1：领域演进与真实编程会话仍是两条链

项目书要求以 Project/Session/Turn 为持久上下文，允许连续开发及重启后继续。实际 [engine.rs](../../../NoManCode/rust-app/src/engine.rs) 第 442～456 行明确拒绝带 tools、allow_commands、write_scopes 或工具历史的 `send_chat_turn`；[web/app.js](../../../NoManCode/rust-app/web/app.js) 第 19 行仍通过 `/runs` 创建对话、通过同一 task 的 `/resume` 继续。

旧页面也没有审批卡片/决定操作；等待审批状态没有完整交互承接，审批需借助现有 CLI/HTTP。第 30 行已有 changes/restore 接口，但这不能弥补会话、审批和继续动作的整体串联。以上属于静态源码证据，本轮没有浏览器实测，不能据此断言页面必然死锁或服务不可用。

恢复后原 task 后续写被封存是已验收安全契约，见 [B review 1.4](<../../员工B/审查记录/第三轮/员工B review 1.4.md>)。然而用户“恢复后继续”的后续 Task/Turn 衔接尚未形成完整客户端流程。

判断：无工具连续 Turn 是合法早期切片；把其完成长期等同“连续编程会话已完成”则偏离项目目标。现有报告已披露限制，本次指出应从披露缺口推进到解决缺口。

关闭标准：先冻结唯一的对外编程会话语义，明确新一轮用户消息与 Task/Turn 的关系、旧 resume 兼容行为、工具消息关联、恢复后新任务承接及重启查询。允许做有边界的桥接，不要求一次性迁移所有旧 Run；不得简单去掉 tool-free 检查或恢复封存来获得表面可用。CLI 先完成整条交互，fallback 维持可启动，后续 UI 接同一协议。

### DIR-04 / P2：网络能力的总体契约尚未与现有审批范围对齐

项目书 §5.1 写明写入、命令和网络均经过审批。[approval.rs](../../../NoManCode/rust-app/src/approval.rs) 第 136～149 行的现有策略覆盖写文件和命令；Provider 网络请求由 Engine 直接发起。不能据此宣称任意网络请求已受逐次 Capability 审批，也不能把批准一条 shell 命令解释为对子进程所有网络行为都有独立约束。

判断：这是项目级权限契约待收口，不是本轮已证明的泄密漏洞，也不是推翻 AP01～AP20 验收。应在生产装配契约中明确模型请求的用户授权粒度、目标绑定与凭据边界，区分模型网络、显式网络工具和命令内网络。是否按配置/会话授权或每次调用决定，应显式设计并验证；不能未经契约就强加每个模型请求弹窗，或承诺不存在的操作系统网络沙箱。

### DIR-05 / P2：当前导航与历史阶段反复混放

本轮开始时 [人员入口](../../README.md) 仍将 GPT-6-sol 和“Workspace 未合主线”写为当前入口；主线已在 GPT-6-astra 接续后验收整合。经理身份、任务板与总进度虽有最新前置状态，正文又保留多个“当前/下一步”，项目书 §10 仍显示审批待分发。

影响：接任者容易重复派工、错误等待旧服务，或沿用旧优先级。这是实际管理偏移，不能靠增加更多同文前缀长期解决。

本轮先修人员入口、同步本次结论与下一步，并保留历史原文；旧任务/报告/日志不重写。后续当前状态以任务板为准，身份维持短接手卡，详细过程由审查记录和对话日志承接。导航治理不能再取代产品闭环交付。

## 符合方向的工作与仍属合理阶段边界的内容

| 工作 | 判断与边界 |
| --- | --- |
| task+call 隔离、参数/工作区/权限绑定、执行前复核 | 符合项目安全目标；必须保留，不能为方便续聊降低约束。 |
| approved 与 claimed/finished/unknown 分离、事务、取消竞争、真实终止恢复测试 | 符合“不伪造完成”和可恢复目标；有风险驱动的必要验证，不能仅因轮次多就判为过度设计。 |
| schema6→7→8 保全、DPAPI、拒绝持久脱敏后无法恢复的参数 | 符合事实持久化和秘密边界；不通过另存明文、执行替代参数来补体验。 |
| <=256KiB UTF-8 普通文件恢复、单 Host 协调 | 当前契约的保守切片，不等于完整 Workspace。目录/二进制/ACL/ADS/命令回滚须另定范围。 |
| Git Diff、Checkpoint、完整 Provider 治理尚缺 | 是阶段一仍需交付的能力；当前缺失不自动构成偏移，但不能永久通过各任务排除项取消项目要求。 |
| Desktop、完整 Team/MCP/Skills 暂缓 | 符合先后端与 CLI、先单 Agent 的项目顺序。员工并行开发也不等于产品必须先做多 Agent。 |

没有足够工时/成本数据判定安全验证投入过度；本次的偏移判断依据生产调用关系与用户验收缺口，不按测试数量、文档数量或代码行数衡量完成度。

## 建议的纠偏顺序与经理责任

1. 下一管理交付先给出一个贯通切片契约：同一 Session 下的工具会话、恢复后新 Task、CLI 最小命令与真实验收脚本；为插件装配留出明确且必须实施的边界。按当前已验收基线登记依赖和唯一写入人，不能直接恢复旧 B/C 任务。
2. 实现最小 builtin 工具生产装配与会话桥接，再让 CLI 贯通。无依赖的 CLI 展示/测试可并行，公共 DTO、Engine 与 Store 必须冻结接口和写入人；不以全量插件化、全量历史迁移作为起步前置条件。
3. 用确定性本地 Provider/临时项目做端到端验收：读文件→审批拒绝无写入→批准恰当调用→修改/测试→事件及真实 Diff→恢复→新 Task 继续。另做真实 Host 停止/重启、审批重复请求和执行结果不明场景；不需要付费 live。
4. 将缺失的 Git Diff/最小 Checkpoint 明确纳入阶段一后续小切片；在完整验收前继续称“后端部分能力已验收”，不称“CLI 工作台已交付”。高级扩展和 Desktop 不提前。

根因主要是经理按模块/文件所有权安排切片，较少以完整用户路径安排联合验收。修复优先级由经理承担，不能把员工依明确范围完成的成果重新定为失败。上述为审查后的建议与下一管理工作，尚未生成新员工实现任务或新的源码写权。
