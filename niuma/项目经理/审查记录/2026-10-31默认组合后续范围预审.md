## 结论

先寻找能交付真实控制能力的最小切片，不预定新增组合根。现有 Engine::new/assemble 已持有实际运行时，仅搬字段或增加版本清单不能证明架构改善。后续应优先评估公开持久 Agent 管理，最终覆盖 Provider 及默认组合；本切片不能取消其他默认能力。

Agent 新增独立 sidecar 不能仅以“旧表有两行白名单”证明合理。经理复读 plugin_management 的现有通用 plugin_id、desired、CAS 与全局 key 主键；复制账本和独立幂等域会产生额外长期边界。条件性优先复用现有持久账本、严格升级迁移，并保留旧列表协议，给 Agent 使用适合其生命周期的 DTO。是否采用专用 HTTP 路径与是否分表是两个独立决定。

## 正式契约前必须闭合

1. schema13 到新版本的验证分支、事务重建及旧行/rowid/receipt/外键/marker 保全；新库重开严格验新结构，不能全局放宽旧版验证。
2. 旧 files/shell 列表和严格 CLI 的兼容策略；新增 Agent 状态不塞入 FilesRuntimeStatus。跨插件同 key 的冲突域必须明确。
3. Agent 的持久意图提交与新 lease 准入如何在线性化点协调；不在插件回调内持 Store 锁，不跨 await 持控制锁，不能用状态快照代替真实准入。
4. draining 期间 enable 的确定语义、已提交 desired 与 actual 不一致时的回执和诊断、失败重试与重启规则。持久回执不等于运行态成功。
5. desired=false 仍能启动 Host、读配置和恢复事实；异步创建的任务回执与运行期失败保持区分。Provider 的在途撤销和 Agent 排空不能强套同一状态机。
6. 真实公开 Host/CLI、历史库升级、CAS/幂等、故障提交点、kill+wait 与重复恢复的验收矩阵，以及唯一所有权。
