## 首次失败：claim 前项目探测

`Engine::create_project_worktree` 依次处理规范化、幂等回放、Store inventory/roots、配置 revision、RootIdentity、`prepare`，再逐 root 的 `probe_project_git`，然后 `claim_worktree`，提交后无 await 地 spawn 持有 worker。`ClaimCommitted` 探针在 spawn 后的 worker 中；该测试要在此处持住 worker，取消 caller 后放行，验证唯一 reservation/origin、最终成功及幂等重放。现有测试的 10 秒从 caller 创建开始，不是产品服务等级或纯同步响应期限，包含真实文件系统与 Git 准备。

1. `prepare` 的 clean inspect 14 次：`rev-parse --show-toplevel`、`--is-bare-repository`、`--absolute-git-dir`、`--path-format=absolute --git-common-dir`；`config --file ... --no-includes --null --list`；`rev-parse --show-object-format`、`rev-parse --verify ... 2. 源项目自身再次进入 `probe_project_git` 的非 clean inspect，省略 `ls-files` 和 `status`，其余12次。共 15+12=27；额外项目也各有自己的实际探测，不可据单项目数量推广。

每个只读 `git()` 命令单独使用 10 秒 deadline；超时/错误后 helper 再尝试 kill 和至多5秒 wait。deadline 从命令创建后、spawn 前计算，包含 spawn 及读管道和 wait；同步命令构造、文件身份检查等并未计入该单个 deadline。不能由此推导整条调用有严格 270 秒上界。第15项 exit1 是 `show-ref` 明确表示目标分支不存在，`branch_available` 将其视为成功，并非该次错误。

## 第二次失败：created 前不可归因

真实进程测试的父端分别对 claim、created、registered 等待 ready 文件，每阶段从启动子进程起给20秒；子进程在目标 probe 写 ready 后阻塞40秒以待父端真实 kill/wait。created 之前除上述 claim 前27次命令，还按当前成功路径执行：claim 后 source clean inspect 14次、分支复查1次、策略准备后的 source clean inspect 14次、`git worktree add` 1次（独立30秒 deadline）、成功后的 source clean inspect 14次、目标 clean inspect 14次和 `worktree list --porcelain -z` 1次，合计 **59次 Git 调用**，另含身份、目录、index 和策略检查；源项目总计约86次 Git 调用才到 created 探针。若实际提前失败则后续调用不会发生，命令数不构成总时长保证。registered 还须真实 Store 登记。

因此单次 worktree add 就可能合法运行长于父端总20秒，且前后多次检查各自有10秒上限；现有20秒测试不能代表生产整个合法调用窗口。原日志仅有 claim 阶段 PID 53108 真 kill/wait 和 `created child stop timeout`；没有 created 子进程的持久阶段、原 PID/退出码或其 Git 事件日志，无法判定是否启动、停在准备、执行 add、创建后检查或其他阶段。超时分支源码调用 kill/wait 不能补成缺失的实际 PID/状态；第二子场景没有可用 retained child.log。最小新增诊断是在该子进程入口安装现有 test-only `worktree_diagnostics::scope`，把阶段、递增命令序号、spawn/wait/退出种类写到父可读的本次独立 fixture，同时记录原子 ready、各 probe、父 child PID/创建身份及 kill/wait；不得写参数、路径、token或 SQL。必须在由经理批准的新固定候选上执行，不能回写旧现场。

## 修正选择：分阶段可证明的有界同步

推荐先限 **测试夹具** 修改 `src/worktree_management.rs` 和必要的 test-only `src/worktree_diagnostics.rs`；若复用 Job/句柄代码确有需要，另经经理明确 `src/process_test_fixture.rs` 写权。保持全部真实 Engine 路径、Store claim、三停点、原 caller abort/worker继续、原文件/索引/refs/receipt/重复执行断言。方案不是直接把10/20改成某个大常数，也不是去掉 deadline：

1. 给两个用例增加明确的准备/执行阶段观测；对第二个子进程在启动后、进入 Engine 前增加父确认闸门，使父先取得原进程句柄并建立进程树收容，之后再允许业务运行。持久记录阶段事件和每个 Git 的开始/结束、退出类别。保留 `try_wait` 提前退出失败，不能把异常退出当 ready。
2. 用**有限总预算加有限无进展预算**监管到达探针。对受监控 Git，根据实际 helper 读命令10秒和清理最多5秒、mutating add 30秒和清理最多5秒设置对应观察上限；状态转换应由受控事件序号确认，不由固定 sleep 或文件 mtime/任意输出反复续期。针对固定单项目路径，使用上述27/59命令的可核计数作为总预算计算输入，并对超量或非法阶段失败；本地身份/Store/调度没有现成形式化上限，单列有界准备/调度余量，由经理明确裁决并以失败诊断记录，不声称数学证明的产品总上界。允许差异路径显式以阶段预算覆盖，不能给额外 project 静默套用单 root 上限。
3. **到达目标 probe 后**单独启动短的、明确有界握手：首个测试必须证明 caller 仍 pending、确实 abort 并 await cancelled、唯一 reservation，再 release worker；三停点必须验证真实状态后立即 kill/wait 原 child，验证非成功退出、同一 operation 恢复/不可重复副作用。原探针40秒防失控上界可保留；成功不能仅靠阶段事件或更长准备窗口。
4. 失败时严格回收：子进程测试使用原始句柄+Windows Job（无 breakaway、父确认赋值后才允许 child 启动后代），终止整个 job、wait 及确认 active=0；记录原 child 身份、signal/exit及失败阶段。首个异步 caller 超时须 abort 并 await，且等待已启动 Git 的受控清理/原句柄信号；若当前架构不能证明子孙已清理，改为同测试逻辑在受监督子进程中运行并使用同样 Job 握手，而不是只记录 PID 或仅 kill 最外层。仅收容本 fixture 进程，禁止泛杀。失败现场保留；活库采样仍标非一致。
5. 原 15秒“取消后最终登记”也包含 59 次真实操作，其与各自预算存在同类矛盾。应另设完成阶段的有限总预算/无进展监控，同时保留“取消后 worker 必须完成、唯一登记和重放”的严格结果；不得把超时当跳过。若观测/收容实现无法与现有权限或时序保持，停止交经理而非放宽为任意结果。

测试护栏：在不改生产期限与默认并发下增加确定性负控，至少覆盖提前子进程退出、无进展 watchdog、探针已到但未完成 kill/wait、故意遗留后代时 Job 回收、以及成功状态后不重复执行；每个要验证观察的前提、错误类别、原进程/后代退出和现场，而非只匹配字符串。先固定静态提交让经理审查，再依其签发的完整独立七步从头执行，首失败停；不单独反复重跑旧失败以宣布根因。若预算/Job 设计涉及扩大文件写权，先明确派单。
