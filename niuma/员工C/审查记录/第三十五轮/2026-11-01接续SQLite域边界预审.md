# NEXT-21U 接续 SQLite 域边界预审

2026-11-01，项目经理。CHANGES_REQUIRED（交接中未接线草稿，不是最终候选）。主线仍 W1-ID01/schema17。读取 C34/C35、正式任务与交接原始快照，未编译、运行数据库或进程测试。

## U35-P01：对象仲裁不等于 SQLite 日志域统一

交接快照 execution_authority.rs 的 FileIdentity::from_file 仅要求 nNumberOfLinks > 0；domain_lock_covers_second_directory_and_late_hard_link 在新增硬链接后仍要求 owner.verify_database 成功，释放原 owner 后允许另一目录取得执行权。这只检验文件对象 mutex，不能证明 SQLite 恢复域一致。

已实际读取 [SQLite 损坏原因 2.6](https://www.sqlite.org/howtocorrupt.html)：同一数据库经不同名称打开会使用不同 journal/WAL，崩溃恢复可能寻找错误日志。[SQLite WAL 第4、7节](https://www.sqlite.org/wal.html)说明 WAL 属于数据库持久状态，异常退出后可以保留；共享内存实现依赖同目录文件。以上为原理来源，不是本项目动态证据。

恢复原 ID 期间实际模型为 gpt-6-astra，经理发现后停写关闭。它留下单硬链接检查、closed 封门、canonicalize 和测试预期的静态增量；文件 SHA256 147451294aed542026272ea6f4f341e454e2892932ac667dd130110e644c55f4，17417字节。保留该贡献但未验收，指定 Terra 接续者须按实际差异自审，不能仅据新增检查声称问题闭合。

本问题沿原任务落实，不能只把原 OS 竞争测试改绿：

1. 所有生产 Store 打开先验证受支持域，数据库多硬链接在 SQLite 有副作用打开前拒绝；持有期检查失败永久封门，并在实际准入/事务提交路径生效。检查错误与真实链接数变化均不能继续执行。
2. 合法大小写/相对路径等必须导向同一受约束 DB 和日志域，或在任何 SQLite 副作用之前明确拒绝。普通读写 Store、只读查询、维护初始化、Engine 恢复须复用同一路径规则。目录/数据库 pin 与 SQLite 打开的实际对象必须有可核关联，不能仅比较两个用户路径字符串。
3. 首次建库在 bootstrap 下固定对象，迁移/初始化只在排他取得后发生；已有库打开不能因竞争失败提前改 schema/settings/recovery。发现不一致不改锁到另一个对象，也不自动删除/移动 WAL/SHM/journal。
4. 测试真实开启 WAL，关闭自动 checkpoint，提交有唯一标记的事务并保留活连接，证明有未 checkpoint 的持久数据；从外部强杀实际持连接 helper，等待同一进程对象退出。随后别名打开应在产品入口拒绝，正路径应恢复该标记并保持完整性。不要正常 drop 连接触发最终 checkpoint 再声称 crash-WAL 用例成立。
5. 覆盖启动前硬链接、持有期新增链接、原 owner 死亡后别名接手、普通 Store 别名、正常多 Store 正控。攻击准备失败列未覆盖；无法证明原对象终止则 unknown 停止后续进程启动。

## 关键节点反馈：先证明现有 pin 的不变量

Terra 接续者已补 SQLite 文件名与 crash-WAL 测试源码，但指出离散 link-count 读取可能漏过瞬时链接。经理不将这一可能性直接当成需要新增监控基础设施的结论：现有数据库 pin 为正常读写句柄，share mode 不含 DELETE。[CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew)明示这种共享模式排斥新的 DELETE 访问，已存在冲突句柄也会使 pin 打开失败；[DeleteFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-deletefilew)及[扩展 disposition](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntddk/ns-ntddk-_file_disposition_information_ex)说明普通删除共享约束与 POSIX disposition 的 DELETE 访问要求。

待验证推断：有效 no-delete pin 期间即使可新增硬链接，也未必可删除它；因此“出现又消失”需先给真实反例。员工应测试创建/删除/rename、预持 DELETE 句柄、适用的 disposition/POSIX 路径和普通 SQLite 正控，核同对象而不凭路径推测。此前测试在 owner 仍持 pin 时直接 remove_file(alias).unwrap() 可能是错误夹具，不能强行满足。封门在每个受保护准入/事务校验生效，任务不要求另起异步文件监控服务。

SQLite 真实对象锚优先核 [WIN32_GET_HANDLE 文件控制接口](https://www.sqlite.org/c3ref/c_fcntl_begin_atomic_write.html)与本地 bundled 实现；取得的借用句柄只查身份，不关闭、不转移所有权。文件名检查保留为辅助。helper 必须显式 ignore、缺环境失败、父方 exact/ignored；父方用 RAII 保证异常路径收割，unknown 停后续启动。

经理允许先固定这一最小完整前置机制供集中静审及有限组件窗口，随后继续 Store/Engine 全入口；该节点不得称 NEXT-21U 完成或合主线。仍未开动态窗口。
