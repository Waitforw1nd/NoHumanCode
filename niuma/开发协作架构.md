# NoHumanCode 开发协作架构

版本：1.0 · 2026-09-23。负责解释人员、任务、代码所有权和交接如何配合；产品技术方向仍由 [项目书](../PROJECT-BOOK.md) 决定，Git 操作由 [Git 规范](../Git协作规范.md) 约束。本次调整协作方式，不迁移或重构产品实现。

## 1. 从入口恢复，再按任务工作

项目经理使用根 [经理启动提示词](../项目经理启动提示词.md)，员工使用根 [员工启动提示词](../员工启动提示词.md)。两者都先读 AGENTS，再核对岗位身份、任务板与实际仓库。角色、任务或文件访问能力不明时先只读核对；有明确任务即可直接执行其已授权范围，不重复索取许可。

| 角色 | 常驻职责 | 本轮未派发任务时 |
| --- | --- | --- |
| 用户 | 产品取舍、分发任务提示词、转交报告 | 不需要代替经理补齐契约或逐条批准普通实现细节 |
| 项目经理 | 方向、契约、任务包、所有权、review、验收、Git 整合与交接 | 根据任务板准备下一份管理交付 |
| A | 领域、Repository、迁移与数据不变量 | 保留已验收基础，等具体任务；不自动代改 B 的 Store |
| B | 应用命令、执行协调、幂等与恢复 | 提供已验收契约作为后续依据；不自行扩大应用层范围 |
| C | HTTP/SSE 与协议适配 | 新接口需新任务；不把历史并行提示词当持续授权 |
| D | 插件声明目录与依赖解析的当前切片 | 无有效派发时不实施；D-R1-01模型由用户指定SWE2max，后续职责/模型按新任务 |

员工默认使用Grok 4.7实现、调试和正式测试；用户对具体任务明确指定其他模型时按任务记录执行（本次D-R1-01为SWE2max），不自动更改其他员工。经理的只读模拟、审查辅助不构成员工派工，不能冒充员工实现或独立产品验收。经理接管产品实现仍须用户明确授权并记录贡献。

## 2. 状态只在规定位置维护

| 信息 | 主要维护位置 | 维护人 |
| --- | --- | --- |
| 全局任务顺序、已派发事项、人员占用 | [当前任务板](项目经理/当前任务板.md) | 经理 |
| 每项任务目标、修订、写入范围、基线和交付 | 对应岗位的任务单 | 经理；员工提出建议，不自行扩大 |
| 本岗位恢复入口、实际执行进度、交接第一步 | 本人的个人身份认知 | 员工；经理同步验收时注明作者 |
| 实际实现、测试、未完成与交付版本 | 员工提交报告及证据 | 实现/验证员工 |
| 放行、返工问题与具体解决思路 | 被审员工的审查记录 | 经理 |
| 提交、验收与合并版本映射 | [Git 整合记录](模板/Git整合记录模板.md) | 经理或指定整合人 |
| 过程与历史 | 经理进度/对话、历轮报告/review | 各自责任人；不把旧“当前”当新指令 |

入口、README、启动提示词只保留流程和导航，不反复复制动态状态。状态冲突时先核对用户最新明确指令、任务修订、有效 review 与实际文件；新收到的有效派发可能尚未登记，不因任务板更新延迟重复向用户确认。员工记录收到的任务来源，经理再同步全局状态。

## 3. 任务状态与分发依据

任务状态依次为：**草案待派发 → 已派发 → 执行中 → 提交待审 → 返工 / 按范围通过**。阻塞可出现在执行或返工中，必须记录原因与可继续部分；取消/替代写明新任务依据，不能默默删除原任务。

- 草案是经理已写出的方案；“文件存在”不表示用户已分发。
- 用户在当前对话明确交付任务、转发经理的有效任务包，或确认分发，构成派发依据。员工登记任务 ID、修订、来源和接手时间后直接工作；不再要求一次形式确认。
- 员工无新任务且上一轮已通过时，回复已恢复、待派发，结束本次接手；无需空跑测试或写一份虚假实现报告。经理按任务板推进下一份管理交付。
- 仅给旧提示词或旧报告路径时，先对照当前状态和最新 review。已结项内容按历史查证；用户明确要求重开则经理形成带新范围/修订的任务，不沿用失效写权限。
- 返工沿用问题编号与当前任务；范围变化先修订任务，更新受影响所有权和验收项。

任务状态与 Git 的“报告提交、Git 提交、经理验收、合并、发布”分别记录。按范围通过不自动表示已合并或已发布。

## 4. 并行与技术边界

每个可验收切片有一个实现负责人，其他角色的支持任务需列明只读、测试或写入范围。独立工作树仍不能使公共契约拥有两个未经协调的写入人。任务开始前列文件所有权与依赖，整合串行进行；共享工作树的暂存和提交仅由经理执行。

当前技术责任链保持：HTTP/CLI/Desktop 适配 → Engine 应用命令 → 领域/Store/Repository 事务与事件；权限、凭据、插件生命周期由稳定 Host 管理。传输层不得自行复制幂等、状态机或领域 SQL。这是分工约束，不宣称尚未交付的插件、审批或 CLI 已完成。

当前双线为C接Turn HTTP、D准备插件声明目录/依赖解析，具体范围与模型按[双线协调](项目经理/任务/2026-09-23C-D双线协调.md)。A/B已验收契约可作依据，但支持子任务也须实际派发。执行顺序与派发状态由任务板维护，不从岗位推断写权。

## 5. 换对话与同岗位并发

一个岗位档案可以跨对话复用，但同一任务只能有一个当前执行者。新对话先核对身份中执行标识、任务修订和仓库差异；用户明确让新对话接手即记录交接，不自动新开任务。

出现旧对话仍在写入的明确迹象时，先暂停重叠文件的修改，由经理协调交接；不能仅凭修改时间猜测无人工作。对不冲突的阅读和准备继续推进，不用新工作树掩盖同一任务的双重所有权。

结束前保存：当前任务和实际阶段、候选版本/未提交差异、报告与 review 入口、未完成项、下一条具体动作、是否仍有已知执行者。员工维护本人身份；经理同步任务板与总进度。随后可以关闭或归档对话，代码与岗位记录继续留在仓库。

## 6. 交付和审查

经理先完成契约/范围/验收矩阵，再给出可分发提示词；员工按 [任务](模板/任务说明模板.md)、[报告](模板/提交报告模板.md) 和 [身份](模板/个人身份认知模板.md) 模板落盘。经理按 [审查模板](模板/审查记录模板.md) 给明确结论，连续两次未解决提供具体修法。

文档或接手演练只做相关检查，不为流程重跑产品测试。历史验收数只能注明为历史；模拟接手通过不代表产品通过。经理接手后应推进任务板中的实际管理交付，不重复已完成的资料重组。
