## 1. 现行调用图与状态归属

```text
Engine::launch -> run_task [任务 Agent lease]
  -> reconcile_open_tools [仅按 task.messages 找 unanswered]
  -> 保存 assistant 工具组 -> Agent AfterCompletion 建议逐项 vote
      Deny -> record_tool_result
      ApplyHostPolicy -> execute_or_wait -> definitions/project/cancel 校验
        Host Allow -> ToolRuntime.acquire(锁内 Store 检查) -> perform_tool
        Host Deny -> record_tool_result
        RequireApproval -> ensure_approval -> wait_for_approval
          用户拒绝/取消 -> record_tool_result [取消再退出]
          批准 -> ToolRuntime.acquire(锁内 Store::claim_approval) -> perform_tool
  -> 结果后继续模型轮次 -> launch 终态 save_task
```

- `engine.rs:1957–2045` 先校验并持久化完整 assistant 调用组，再让 Agent 建议；新组禁止撞已有审批 `Store::save_new_assistant_group`。Agent 的 Deny 不获得 ToolLease、不创建批准写执行权；非法 ToolVote、未授权定义或解析失败是任务错误，不应伪装已执行的结果。Host `approval::evaluate` 将 read/list/search 分为 None、write/command 必须审批、未知拒绝；`run_wasm` 当前由执行入口直接拒绝，不能据分类表推断它已开放。
- 单个 `ToolRuntime` 在 Engine 组合时装配：files/shell 各自短锁和在途计数，`acquire` 持相应短锁执行有限 Store admission/claim，lease 才可执行。Agent task lease 与 Provider Completion lease 是独立资源，不得在应用服务中复制。`Engine.gate` 是既有 async 工作区/其他业务协调门；`write_file` 持同一个 gate 跨文件预检/执行/结果，不是通用数据库锁，抽离时不能新建一把替代。
- `decide_approval_with_network_ack` 在 Store 事务提交用户决定/网络确认后取 waiter 发送；`wait_for_approval` 先登记 oneshot 再读持久状态，100ms 轮询防丢通知，取消时移除 waiter 并持久取消待处理审批。waiter 只是内存唤醒提示，审批表是权威；锁不得跨 await，丢通知或另一个 Store 的决定不能使已经提交状态永久不可见。外部公开 Engine 方法和 HTTP/CLI 语义应维持。
- approved claim 由 `Store::claim_approval` 在 IMMEDIATE 核 task/call/name/args、审批 binding、项目配置、运行态和持久 files/shell、网络确认及 reservation 后原子改 claimed；已 claim 后取消不能倒写成未执行。`perform_tool` 的 write 还在 workspace gate 下读取前态、准备 change、重查 digest；命令 unknown 直接返回 `ApprovalError::UnknownResult`，不生成成功消息、不重发。write 执行成功后提交失败会尽力标 change unknown；不论内存错误还是重启 `Store::recover` 都不得把 claimed/prepared 当可重试执行权。
- 已批准完成路径 `finish_approval_with_change` 在同一事务写 Task/TurnTask 投影、`tool_result`、workspace change/file_backup 及 finished（`store.rs:1740–1796`），成功后 Engine 才在本地 task 追加。预检失败的非数据库错误也用该批准事务写安全错误；数据库错误直接返回。当前非审批路径 `record_tool_result` 先独立 `Store::event` 事务，再修改内存 Task，最后独立 `save_task`；事件、消息不是同一提交。
- `Store::save_task_tx` 以 tasks.value 的 Task 为承载并同步 TurnTask/Turn 状态事件；对已持久 cancelled 的旧快照保留 cancelled/error，但现接口并未对 messages 全前缀提供普遍 CAS。`launch` 的终态保存继续使用运行中的可变 Task（`engine.rs:1749–1799`），不能仅移动 result 方法就宣称状态权威或修复旧快照竞争。

## 2. 恢复与两步提交的条件反例

`Store::recover` 对 queued/running 从 `delta` 事件重建 output、标 interrupted，claimed approvals / prepared changes 转 unknown；没有把 `tool_result` 事件重建到 task.messages（`store.rs:1801–1858`）。`Engine::resume` 和 `unanswered_tool_calls` 只看持久消息中 call/answer，不查事件；重启后 `reconcile_open_tools` 对无 approval 的未回答 call 写固定 interrupted 文本，对 denied/cancelled approval 写对应错误，二者均再次调用 `record_tool_result`。

**可按代码静态构造，但本轮未运行：**已持久 assistant group；普通 read（或 Agent/Host 否决）`Store::event(tool_result)` 成功提交；进程在内存追加/Task save 成功前真实退出。重启 recover 不回填该消息；满足 resume 的其他前置后，None approval 对账追加 interrupted 事件与一条消息。原事件仍在，原结果没有被证明从磁盘删除，但当前 transcript 不恢复它，且同 call 会有两条 `tool_result`。如任务最终 completed，后续 chat 续接 `chat_completed_prefix` 对每个新 closed call 要求对应事件数相等并按位置比较（`store.rs:2192–2219`），两条事件对应一条消息可返回 `UnsupportedSession`；这不是凭结构宣称已运行复现，也不保证所有任务都能走到后续 chat 校验。拒绝/取消有对应审批时亦应独立覆盖，不能把无审批的 interrupted 替换误称为真实写入成功。

**普通 `save_task` 返回错误不同：**`record_tool_result` 此时已在调用方内存追加消息；run_task 返回错误后 `launch` 尝试用同一 task 再保存 failed/cancelled 终态，若该保存成功，可能补上已存在的结果消息。若再保存也失败、或两次保存之间进程退出，才可能留下上述事件/消息缺口；不可把每次 save 错误直接断言为丢失。对已批准路径，finish 事务失败不会产生半个同事务结果；若真实副作用已发生而 commit 不确定，claimed/prepared/unknown 边界仍须保守诊断，不能为了去重重新执行。

## 3. 建议真正缩小 Engine 职责的边界

建议新 `ToolCallApplication` 为唯一应用服务，Engine 仍为装配根和公开兼容入口，注入具体依赖，不传 `&Engine`、不通过反向任意回调取字段：

```rust
// 精确名称/所有权由正式契约冻结；示意借用、返回类型，不新增外部 API。
struct ToolCallApplication {
    store: Arc<Store>,
    tools: Arc<ToolRuntime>,            // 与 Engine 管理入口共享同一实例
    workspace_gate: Arc<tokio::sync::Mutex<()>>, // 同现有 gate，绝不复制锁
    approval_notifier: Arc<ApprovalNotifier>,   // 同一注册表；持久事实在 Store
    probes: TestOnlyScopedProbes,        // 仅 cfg(test)，按 task 隔离
}
async fn apply_vote(&self, task: &mut Task, call: &ValidatedCall,
    vote: ToolVote, redactor: &Redactor, cancel: &CancellationToken) -> Result<()>;
async fn reconcile(&self, task: &mut Task, redactor: &Redactor,
    cancel: &CancellationToken) -> Result<()>;
fn decide_approval(&self, id: &str, decision: ApprovalDecision) -> Result<ApprovalRecord>;
```

`ValidatedCall` 只含当前组确定的 call_id/name/args 和必要上下文，不是承诺通过 Agent 取得权限；需要重新核持久消息、任务/project/作用域、Host policy 和 ToolRuntime admission。`Redactor` 是受限的清洗能力，不能持久化凭据；task/args/错误事件均沿用 secrets::redact_persisted 与既有特定 key 清洗。Engine 保留模型轮次、Agent 前后投票、网络/预算、任务调度/取消公开入口、生命周期装配与汇总；退出实际审批等待、Host 工具决策、单次租约执行、write preflight、结果提交及调用组对账。原 `Engine::decide_approval[_with_network_ack]` 保留签名并薄委托；其它引擎调用如 resume 必须只依赖有界的只读/对账接口，而不是暴露整个 Engine。

`Arc` 只共享现有唯一实例，不能构造第二套 ToolRuntime/approval registry/gate；确认 `Engine.gate` 还为别的入口服务，完整消费/调用链不变。锁序沿既有：可选 workspace async gate → 单一 ToolRuntime 短锁 → Store/db → SQLite；不持同步锁跨 await，通知锁仅注册/移除，不在锁内调用未知回调。已准入 lease 跨必要异步执行，调用/析构不在 runtime/Store 短锁内。原 task-id 绑定 probes 须搬到服务可见的受限 test-only 结构并经同一真实路径触发；不得通过 test 实现反向拿 Engine。拆分后对同一 task 同一 in-process owner，跨 Store 仍由事务和持久检查决定，不能仅靠内存 mutex。

## 4. 结果权威、原子提交与兼容

建议第一功能切片仅统一**非 claimed**结果，不先重写成熟的已批准完成事务；两者可共享事务内的狭窄校验/追加 helper。候选 Store 能力：

```rust
enum UnclaimedOutcome<'a> {
    ReadCompleted(&'a Value), AgentDenied, HostDenied,
    UserDenied { approval_id: &'a str }, Cancelled { approval_id: &'a str },
    InterruptedWithoutClaim,
}
fn commit_unclaimed_result(&self, expected: &TaskPrefix, call: &CallIdentity,
    outcome: UnclaimedOutcome<'_>) -> Result<CommitResult>;
// CommitResult 返回持久权威 Task/投影与 Inserted | Replayed；失败不得先改调用方内存。
```

这只是拟议内部类型，不将裸 enum 当安全凭据：生产服务独占构造，Store 在同一 IMMEDIATE 事务从 `tasks`/TurnTask 和事件重新读权威事实，验证 task/run/turn/session、assistant group 的 call_id/name、参数经脱敏后的绑定、唯一 ID、当前可回答位置/消息前缀、调用者预期前缀或 revision 等；不能只比 caller 提供的 Task，也不能把 `validate_call_history` 仅验证唯一 ID 当作已证明顺序或完整前缀。对 ReadCompleted 必须有 Host 实际获取的 read lease 与严格只读分类；AgentDenied/HostDenied 只能产生固定错误；UserDenied/Cancelled 验证持久审批绑定和实际决定；InterruptedWithoutClaim 只能产生固定 interrupted 安全文本。无审批结果不得被解释为批准 write/command 成功。是否允许对未知类别拒绝以及对未来新增工具如何升级，须由正式契约封闭类型集合。

事务内先识别同一 `(task_id, call_id)` 的可信已有消息与事件：唯一匹配、同语义返回原 canonical 结果与当前持久 Task，不重复追加；不同 name/content/source、重复或不相容事实返回安全冲突，不覆盖。先对 Value/字符串统一使用现有 persisted redaction 与 canonical 序列化，再比较事件 result 和 message 内容，避免原样秘密、JSON 文本/值差异及 key 替换不一致；不能信任调用者传入任意 `approval_id` 以伪装审批。新结果的 Task 消息和 `tool_result` 事件在一事务中提交，保持旧事件结构和正序；commit 失败或不确定的返回需明确 unknown/可查证，服务只有 commit 成功或可信同结果 replay 后才更新本地 task。

取消并发必须明确线性化：Store 读最新状态，保留现行 `save_task_tx` 对 cancelled/error 的保护；已批准并 claim 的真实结果在取消后仍可按原事务写入，未领取不得新增副作用。已完成的只读结果或固定否决结果在取消竞争中是接受还是拒绝，应由经理冻结，但无论哪种不得复活任务或把 unknown 改成功。返回 DB 权威 Task 后，Engine 的后续终态/多轮保存必须基于同一受控前缀合并或冲突失败，不能让旧内存覆盖已提交消息；异常时应显式重新读取权威状态，不能让终态 catch 块将一个未提交的本地候选误写回。

历史策略不可用“事件必须都有 ID”替换当前兼容：`chat_completed_prefix` 已接受无 call_id 的旧只读/拒绝事件，靠归属 task/turn/session、顺序、name、解析后精确 result 验证；保留已正确闭合的旧会话。对当前已存在的孤立/重复/无 ID 事件，要在事务内仅在可唯一证明归属、结果与权限来源时重放/恢复；不能凭顺序猜测副作用成功，也不能一概删除旧事件或只取最后一条。无足够证据的旧异常返回既有安全诊断，必要时给受控修复/继续路径，不能自称所有历史库无损自动修复。特别是原始 Agent Deny 对 write 与中断结果在无审批下都不能被误当成功。

**Agent 拒绝后新 Turn 的独立兼容点：**`agent_runtime_tests.rs:522` 的 A03 使用 Chat，证明同一个任务中 Agent 拒绝 `write_file`、无 approval/文件写入、生成 `blocked_by_agent_policy` 结果后完成及继续模型轮次；该测试没有发起下一 `send_chat_turn`。A01（约 2157 行）验证纯文本首轮后的下一 Turn，但没有先发生 Agent 拒绝；本次检索未找到两者合一的真实新 Turn 覆盖，不能把既有测试称作已证明该用户故事。静态代码在 `chat_continuation_prefix_tx` 中对 `approval::evaluate(...)=RequireApproval` 且无 approval 的 call 返回 `UnresolvedEffects`，未按 Agent 拒绝结果区分，因此满足 A03 同样持久事实且进入该续接校验时，静态推导会阻断新 Turn；命令也有相同条件，但尚未动态复现。该行为是 NEXT-19 明确新增兼容修正范围，不能创建假的 approval、放宽所有无审批写/命令或用错误字符串直接宣称副作用未发生。

可选的无第二账本、保留 schema17 方案：对**新**原子提交在既有 `tool_result` event data 中增加封闭版本化来源，例如 `origin_version:1` 与固定 `agent_denied` / `host_denied` / `approval_denied` / `read_completed` / `interrupted`；Task 消息与事件仍同事务，事件仍是既有证据而非第二结果账本。新续接校验仅在来源、固定错误内容、call 绑定及无 claimed/unknown approval、无相关未决副作用等约束一致时，允许可信的 Agent/Host 明确拒绝作为已闭合的非执行事实；已批准执行仍须真实审批和完成证据。事件来源字段只有由 Host 受限事务写入并校验完整事实才有意义，不能把任意模型内容、任意普通事件或裸字符串当作证明。`Store::event` 现为公开通用写入入口，必须同时确定是否收窄/拒绝外部伪造 `tool_result` 或确保所有可写路径归受信 Host；版本字段本身不是安全凭据。旧无来源或无 call_id 事件仍按现有顺序/name/result兼容，旧 write/command 的拒绝若不能唯一证明是可信未执行，保守返回既有安全诊断，历史如何精确放行由经理裁决；不能因新格式改变直接拒绝全部旧只读或已审批历史。

**schema 决策尚需冻结：**原表 events 已含 task/turn/session、JSON data，task 消息已有 call ID；若正式契约选择扫描并严格校验既有事件，在 IMMEDIATE 事务序列化、只对新调用给唯一结果，可设计为不新增表/迁移，但需证明事件数量、性能、历史无 ID 与冲突收敛；SQLite 没有现成 `(task_id,tool_call_id)` 列级唯一约束。若要求数据库强制唯一、可验证结果来源/版本、或精确修复歧义旧记录，可能需要新索引/表或 schema 版本及严格迁移。不可承诺无迁移后再隐式加第二个结果账本；选择新结构须说明与现有 events/Task 唯一权威的关系和历史数据如何验证。已有已批准完成按当前 claim/change/event/finished 同事务保持，若扩展 replay 必须先设计匹配 finished 回执的读取及冲突检查，不能让重复调用再执行或悄悄改 finished。

## 6. 分阶段与唯一所有权建议（非派工）

建议两个有明确交付的顺序子阶段，避免一次跨 Engine/Store/公开接口大搬迁但最终目标不止封装：

1. **结果事务/历史边界先定并实现。** B 独占 `store.rs`、必要 `repository.rs`/schema 与新内部结果类型，迁移或 no-migration 由契约决定；保留批准写 finished 的现有原子事务。D 独占新旧崩溃、故障、并发和历史兼容测试文件；C 独占真实公开 CLI 用户链测试/文档。涉及既有共用 `engine.rs` 的调用侧仍只指派 B 一人。先验证回滚/取消/旧历史和 no-stale-memory，再进入下一步。
2. **抽离应用服务并删除 Engine 的真实职责。** B 独占新 `tool_call_application.rs`、`engine.rs`、必要 `lib.rs` 与受限 Store helpers；runtime 所有权只能保持共享同一实例，Engine 仅保留装配及兼容委托。D 按正式约定独占新服务/已有 `agent_runtime_tests.rs`、`workspace_crash.rs`、approval/checkpoint 和测试模块；C 独占 server/cli、`first_user_workflow`、`tool_session_turns`/`session_turns` 与文档，实际写入范围由经理核基线与冲突后冻结。共享 `lib.rs` 始终由 B 在真实测试文件合入后单人接线。`tool_runtime.rs` 若需改签名，由经理明确唯一 owner；能用 Arc 共享则不扩大写面。

每阶段独立候选/提交人/整合人、固定 tree、串行窗口和可恢复证据；可先完成同任务内的静态设计/接口，但不能把阶段一纯事务或改文件名当作已完成 Engine 解耦。`N18-F01` 仍 `OPEN_UNATTRIBUTED`：这些改动不构成对其根因的识别或修复。
