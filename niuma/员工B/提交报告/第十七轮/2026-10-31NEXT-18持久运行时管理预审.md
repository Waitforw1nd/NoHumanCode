## 建议 API 与线性化（待冻结）

1. 使用封闭枚举 `RuntimeId::{ChatAgent,CompletionProvider}`、`SetRuntimeEnabled { enabled, expected_revision }` 和既有全局 key 域；`Engine::set_runtime_enabled(id, request, key) -> Result<{receipt,replayed,current}, SafeError>`；`Engine::runtime_status(id)` 返回持久 desired/revision、当前进程快照、scope/capability、converged。receipt 只表示意图已持久接受，不表示 callback 成功；旧回执重放永不触发生命周期。状态中明确 transitioning/failed，converged 必须同 desired、实际 admission/active、transition 和失败状态一起计算；禁止把内存快照表述成其他进程实时状态。
2. 每个实例统一短锁顺序：可选既有 async gate → 对应 runtime state → Store 连接锁 → SQLite 事务；不反向调用、不同时持两类 runtime 锁、不跨 await。Store 不调用运行时或插件；状态采样也 runtime→Store。回调、codec、stop/start、插件/decoder/host 析构均锁外，且不得持事务；生命周期状态先 reserve/取 host 再执行，结束重新取短锁更新。
3. 持 runtime 短锁进入 `Store::apply_runtime_intent` 的 IMMEDIATE 事务：校验后**事务内先查 key**，同参返回原回执，异参冲突；仅全新 key 再检查 Busy、revision，再原子写 desired 和 receipt。因 Busy 是进程内状态，传入短锁下的只读判定值，不能 Store 回调 runtime；Busy 返回须回滚、不消费 key。commit 失败不得改变 admission 或 generation。commit 成功再在同一 runtime 锁下 reserve 本地状态（不运行回调），释放锁后执行回调。单次提交后调用进程崩溃允许持久状态与当前态暂不收敛，重启依据 desired 重建；重放不修复，另行明确显式 reconcile/restart 恢复机制。
4. 同一个 Store 的 Mutex 不跨 Store；所有新准入必须与所有管理写使用同一 SQLite 数据库写序列。建议 `BEGIN IMMEDIATE` 后读对应 desired，持事务至 lease 计数/绑定准备完成并成功 commit；如此与管理写按事务锁顺序确定先后。若 admission 事务赢先于 disable commit，则该 lease 已准入可继续；若 disable commit 先赢，新 lease 必拒。只读 SELECT 后释放事务再计数会有 TOCTOU，不满足此保证。失败或 commit 失败回滚预留计数，lease 不外逸；任何 payload/decoder 析构安排在所有锁与事务释放后。数据库不可用按安全失败，绝不能用缓存 true 放行。IMMEDIATE 每次准入的写锁竞争/性能及事务忙超时是明确代价，需实际测试。
5. Agent 建议 `acquire_persisted(&Store) -> Result<AgentLease>`：runtime 锁检查当前可用、绑定和计数溢出 → Store IMMEDIATE 核 desired → 暂存计数 → commit → 放锁交付 lease。锁内只做可证明安全的受限对象克隆，失败统一释放锁后 drop。Provider 建议 `prepare` 仍可锁外编码，但只作可选早拒，最终 `acquire_persisted(prepared, subject, task)` 在 runtime 锁内核本地 generation/effect，再由 `Store::admit_completion_if_runtime_enabled` 在**同一个 IMMEDIATE 事务**读取 provider desired、执行现有网络权限/预算 admit 并提交，最后交付 lease 和 permit/receipt；要把原 `network_admit` 拆出事务内实现，不能持 DB 锁递归调用自身。预留 in_flight 的溢出与失败回退、permit 的构造及 commit 失败处理须保证无网络发送且不泄露预算；保持原 unknown 语义，不自动重发。实际 admission 以成功提交为界，非 prepare 或调用时刻。
6. 多 Store 禁用后，其他 Engine 的内存 active 可能仍为 true，下一最终准入必须拒绝；不承诺广播或立即析构。随后跨 Store 又 enable 后，旧 Engine 若本地未被 disable 看到且仍 active，是否可以重新准入需经理裁决：安全保守选项是在每次最终准入比较上次观察 revision，变化即拒并安排本地 reconcile，需特别处理 false→true 漏观察；仅比较 enabled 会允许跨进程漏掉的禁用窗口后的旧代次复用。管理 callback 结束重新持 runtime→Store 读取 revision；若不匹配该次操作，不按旧意图开启 admission，标记未收敛并要求受控 reconcile。单次读取也不能替代最终事务准入。

## 状态和冲突建议

| 当前进程状态 | 全新 enable | 全新 disable | 已有 key 重放 |
| --- | --- | --- | --- |
| 已启用且稳定 | CAS 提交新 receipt；无需重复 start | CAS 提交 false，关 admission；Agent 排空，Provider 锁外 stop | 同参返回原 receipt，不驱动；异参冲突 |
| 已禁用且稳定 | CAS 提交 true，reserve start；成功才开准入 | CAS 提交 false，新 receipt，可无动作 | 同上 |
| Agent draining / 任一 transitioning | Busy，不提交或消费 key | 建议允许 CAS 提交 false 但不重复 stop；已提交的相反意图与回调结束复核 revision 必须配套 | 同上，先于 Busy |
| lifecycle failed / 代次耗尽 | 建议拒绝新 enable、不提交；由经理定义显式恢复 | 可提交 false，保持关闭并报告 failed；不假报 stop 成功 | 同上 |
| Store 失败 | 返回安全错误，不改 admission；commit 结果不确定时告知可能已提交，客户端以同 key 查询/重放 | 同左 | 同左，不能猜测 receipt |

对“transitioning 中再次 disable 可提交”的实现要谨慎：若正在 start，先 commit false 并记录最新 revision，start 完成时不得开 admission，随后锁外执行 stop；若不能提供可靠后续驱动，建议所有新意图在 transitioning 返回 Busy，但同 key 重放始终优先。Agent draining 时新 disable 可保持 false、不重新执行 stop；相反 enable 一律 Busy。上表为建议，经理需选定，不能既允许新意图又依赖仅首次回调的过期结果。

## 零激活与失败

- 构造拆为 register/factory 与 start：desired=false 初始化有可供日后启动的未启动 host、admission=false、in_flight=0、无 effect/启动回调；不调用 `start`、绑定解析或伪造已激活状态。desired=true 的 start/绑定失败安全关闭并令 Engine 构造失败；多 runtime 先后激活时后者失败应在锁外受控清理前者。启动 desired 与其他 Store 并发变更也必须在首次准入再次持久核验；不能只靠启动快照。
- Provider `from_host` 当前 start/resolve 使用 `?` 失败时本地 host 在返回路径析构（`provider_runtime.rs:172`），未像 Agent `from_host` 对失败 host drop 使用 guarded。新实现须显式在锁外受控 drop，审查 start panic、部分 effect、绑定失败和 host/plugin 析构 panic，避免双重 panic 中止；捕获失败只报告固定错误，不假称清理成功。Provider `acquire` 失败路径涉及 prepared decoder 和 binding 的析构，所有早退（锁毒化、代次/effect 不符、溢出、admit 失败、commit 失败）都要显式释放 state/事务后再销毁；生命周期回调失败保持 admission 关闭，记录 effect/recovery 及失败，不把已提交 receipt 回滚。
- 最小必要反例：两个独立 Store/Engine 同库，用屏障控制 disable commit 与 Agent/Completion 准入先后；false→true 跨实例代次；prepare 后禁用；同 key replay 与 Busy、异 ID 参数冲突；start/stop 阻塞时并发 disable；每个 commit 前后故障与计数回滚；零激活计数与构造失败析构 panic；Agent 最后 lease Drop 与 enable 竞争；Provider decoder Drop 重入状态查询无死锁；route check 已完成 Models 的拒绝保留 calls；原无工具 Chat 在 files/shell disabled 时可运行。所有用例要固定各自基线与真实运行证据，本次未执行。
