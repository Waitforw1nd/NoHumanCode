## 2. 安全绑定与调用身份（替换修订1 §3.2/§3.3/§3.5相关项）

### 2.1 作用域

- provider 的 `tool_call_id` 不是跨任务全局身份。审批记录 `id` 仍全局唯一；调用关联使用 **UNIQUE(task_id, tool_call_id)**，两列 NOT NULL；不得使用含 NULL 的 turn_id 作为唯一键来规避唯一性。
- 同一 task 的全部 assistant tool_call 历史中 id 必须非空且唯一，包括同组重复及后续组重用。允许 resume 再读取同一条已持久化消息，不把这种读取当作新调用。新组在产生本组任何审批行、备份或执行前完整预检；非法组零新增审批、零执行，任务安全失败。旧历史歧义拒绝恢复，不猜配结果。
- 跨 task 同名 id 独立建卡，不复用决定；同 task 第二条新调用即使参数相同也不能重用旧 id。查询及决定应核对记录归属，关系损坏不是 not-found。

### 2.2 绑定证据

除 `args_digest` 外增加 `binding_digest`，绑定版本标签、task_id、nullable session_id/turn_id、tool_call_id、tool_name、持久化的 workspace 标识、write_scopes、allow_commands 以及规范化参数摘要。字段采用结构化序列化后哈希，不拼接无分隔字符串；公开报告给出精确组成。

规范化参数采用递归对象键排序、数组保留顺序、serde_json 标量语义；JSON 排版与对象键顺序不影响摘要。不要求 `1` 与 `1.0` 等所有数字形式语义等价。参数错配、工具或工作区/权限边界变化 → typed `ApprovalBindingConflict`，零执行、零第二张卡、零新的 resolved。`args_digest` 不能仅作装饰性审计。

建卡时对执行用参数计算摘要；每次取得执行权前重新计算并核对绑定。不得因旧记录 approved 而跳过 definitions、当前 policy 和 workspace 的现有防线。本修订不宣称解决文件系统外部变化/符号链接等全部 TOCTOU 风险，也不把审批当 OS 沙箱。

### 2.3 脱敏与恢复

- preview/审批行/事件仅保存安全摘要和元数据，不增加明文原始参数或秘密快照，不绕开 `redact_persisted`、DPAPI 边界。
- 恢复从既有持久消息获取参数，**与批准时摘要不同就拒绝执行**。脱敏后原值无法安全还原时同样 fail closed，不拿 `[redacted]` 当原命令执行、不猜补、不自动重新批准；要求用户检查后以新调用重新请求。
- 进程内原参数仍须与绑定匹配；不承诺所有含秘密参数都能跨重启继续执行。报告单列这一安全限制。
- denied/cancelled/unknown/binding-conflict 的错误消息使用固定安全文本；preview `write_file` 仅安全相对路径及字节数，`run_command` 经适用脱敏后按 Unicode 字符截断到 160，不能泄漏完整参数/环境/正文。

## 3. 审批决定和执行事实必须分离

审批 `status` 仍为 pending/approved/denied/cancelled。新增持久 `execution_state`：

| 值 | 含义与恢复 |
| --- | --- |
| not_started | 未领取执行权；仅 approved 且任务允许执行时可原子 claim |
| claimed | 执行权已提交；可能未调用/正在调用/已完成但尚未持久结果；重启一律按 unknown，不自动重放 |
| finished | 安全结果、tool 消息与必要投影/事件已共同提交；恢复复用结果，绝不再次 execute |
| unknown | 无法确定外部副作用结果；停止该调用及后续自动工具执行，要求人工核查，不伪造成功 |
| cancelled | 决定之后、执行权领取之前被任务取消；永不执行，后续 resume 产生安全取消结果 |

该字段描述工具尝试，不改变既有 Task/Turn 状态枚举，不引入 Running→AwaitingApproval。denied/cancelled 决定可保持 not_started，由决定状态阻止执行。

### 3.1 顺序

1. 预检工具白名单、调用身份与绑定；建 pending + requested 同事务提交。
2. 决定事务仅 CAS pending→approved/denied；更新 decided_at/by 与 resolved 同事务，提交后通知等待者。
3. 执行前在存储事务内重查审批归属/绑定/status、任务取消状态、execution_state；仅 approved+not_started 且任务未取消时 CAS→claimed。取消先提交则不得 claim。**事务提交成功后**才允许 file_backup、tool_start、workspace::execute。
4. 工具返回后，将安全 tool_result 事件、对应 tool 消息、task/turn 投影与 execution_state=finished 放同一事务提交；失败则整组回滚。正常工具错误可作为真实 error 结果 finished，不得变成成功；无法判断副作用结果的中断保守进入 unknown。
5. recover 仍把 running/queued 任务转 interrupted、保留 pending 决定；claimed→unknown。finished 必须具有相符的已持久结果，缺失即损坏，不自动重做。not_started 的 approved 经 resume 重查绑定后可执行。
6. unknown 不补造 tool 成功结果，也不自动重新向模型请求另一遍相同操作；使用既有非 completed 终态及安全诊断结束本次执行。v1 无“重置 unknown 后自动重试”API；人工核查后的新操作必须新调用、新审批。

外部进程/文件与 SQLite 无共同事务，本任务提供**保守的最多一次自动尝试**，不是分布式恰好一次。claim 后但 execute 前崩溃也可能产生零次执行并进入 unknown，这是明确接受的安全取舍；不引入超时租约自动重试。

### 3.2 取消、等待与并发

- 取消必须有持久事务依据：保存任务取消事实、该任务 pending→cancelled 及各 resolved；approved+not_started→execution_state cancelled，批准决定本身不改写、不新增第二条 resolved。任务取消及领取执行权由同一 Store 事务边界裁决，防止先取消后仍被旧内存副本放行。
- claim 先发生时无法撤销已经发生的外部副作用；取消阻止下一调用。当前调用只有真实结果落库才能 finished，否则 unknown。不能承诺 cancel 一定杀死已经启动的外部命令。
- 后台终态保存不能覆盖已持久的取消事实而误写 completed；resume 应识别 execution_state cancelled，不使原批准重新可用。
- 所有决定/取消竞争只允许一次 pending 状态转换与一次 resolved；未知 id/重复决定返回 typed 错误，无额外写入。
- 通知只是优化，不是事实源：注册等待者后重新读取持久决定，避免建卡到注册之间丢唤醒；每次唤醒重读。可用版本化 watch 或注册后复查，不在数据库锁内 await；取消路径同样不能丢通知。
- 重启无等待者时 decide 只持久化，不能主动 launch/resume/执行工具。

## 4. Schema、兼容与公开 API

- 正式迁移仍为 6→7（7 尚未验收或发布）；原 schema 6 约束/行/数据不放宽。新表明确加入复合唯一键、绑定摘要、执行状态 CHECK 和 task 关系检查；verify 必须核对真实约束而不是仅列名/索引名。
- 迁移 DDL、标记、user_version 按事务与可重入规则设计，不能把旧 schema6 标记与当前7简单比较后拒绝合法升级。断点重开、缺约束伪表、已有数据保持均测试。
- 员工临时修订1 schema7 数据如存在，保留现场；不得删除数据库或把不匹配7标记为通过。可明确拒绝未发布开发版结构，并提供员工测试夹具重建说明，禁止假装兼容升级。真正用户schema6库必须保留并成功迁移。
- 新 typed 错误至少区分 not-found、已决定 conflict、binding conflict、执行结果未知、持久关系损坏；实现 `std::error::Error`，允许传输层通过 error chain 分类，Display 不含参数/秘密。
- 公开查询：按审批id查、按task列出全部/待定记录，确定序 `(created_at,id)`；原任务不变。公开记录提供安全 execution_state，不透出原参数。报告固定真实签名和字段类型，供 C 后续冻结，不能只给语义名。
- Unknown 工具维持 fail-closed：分类 Unknown，evaluate→Deny；新工具即使加入 definitions，在显式安全分类前也不直通。修订1“新工具默认需要审批”不能解释成 Unknown 已获执行许可。
