## 1. 发现

### P1 · B-R2-REDACT-01：完成证据的两条脱敏路径会分叉，使真实已执行审批立即成为损坏状态

触发条件：获批 `run_command` 返回含普通模拟文本 `bearer abc123` 的 stdout。无需真实凭据，也不依赖异常数据库。

候选 `src/engine.rs` 的 `perform_tool` 先把结果对象序列化为 JSON 字符串，再交给 `Store::finish_approval`。`src/store.rs:1041` 起的 `finish_approval` 把该字符串作为 tool message 的 `content`，同时又把字符串解析为 `Value` 写 `tool_result` 事件。保存 task 时，字符串整体经过 `safe_task_value`/`redact_persisted`；事件则对解析后的对象递归脱敏。

候选 `secrets::bearer_end` 对 JSON 字符串中的转义换行看不到真实空白，会把 stdout 后续引号和大括号一起吞掉。实跑得到：

```text
message_content="{\"status\":0,\"stderr\":\"\",\"stdout\":\"bearer [redacted]"
event_result={"status":0,"stderr":"","stdout":"bearer [redacted]\r\n"}
```

前者已不是可解析的结果对象。`src/repository.rs:768` 起的 `validate_approval` 在 finished 状态把 message content 解析失败后作为字符串，再与事件中的结构化 `result` 比较，因不相等返回 typed `CorruptState`。真实命令已执行且审批已写为 finished，但查询审批及后续 resume 会失败，破坏 AP16/AP20 的 finished 可恢复性与 typed 查询可用性。

证据：[最小探针](A-AP12-AUDIT证据/audit_redaction_paths.rs)、[运行日志](A-AP12-AUDIT证据/audit-redaction-paths.log)和[复验说明](A-AP12-AUDIT证据/README.md)。首次裸跑因没有加载 `link.exe`，退出码 1、测试未运行；加载 Visual Studio x64 环境并使用隔离 target 后退出码 0，1/1 探针通过。这里“通过”表示反例稳定复现，不表示产品通过。

建议：完成事务应从同一安全值派生 tool message 与事件，并验证后续 `safe_task_value` 再处理仍保持幂等和语义相等；不能只假定“先结构化脱敏一次”即可。新增真实 `run_command` stdout 覆盖 bearer/赋值式文本，断言 finished 可查询、重启/resume 不损坏、数据库不含原模拟值。

### P2 · B-R2-CANCEL-01：无 active worker 时公开取消先成功持久化，再返回错误

触发条件：任务没有当前进程内 active handle，例如 runtime 停止后仍有 pending 或 approved+not_started 审批。调用公开 `Engine::cancel`。

候选 `src/engine.rs:966-973` 先调用 `Store::cancel_pending_approvals`；后者在 `src/store.rs:933-980` 的 Immediate 事务内提交审批取消事实和必要的 resolved。随后 Engine 才查询 active map；条目不存在便返回“成员当前没有运行中的任务”。因此 API 对同一次调用产生“写成功但响应失败”，调用方无法判断取消是否生效，重试仍报错。

AP18 夹具在 `tests/approval_gate.rs:930-960` 直接调用 Store，绕过了公开 Engine 入口，未覆盖此语义。重启 recover 后 Task 可能是 `interrupted`；本发现只要求审批持久取消、零执行且 Engine 返回与实际效果一致，不要求把 `interrupted` 非法改成 `cancelled`。

建议：把 active token 视为可选；持久取消成功后，有 token 就通知，无 token 也返回成功。增加 runtime 真正停止、重开后调用 `Engine::cancel` 的测试，断言返回成功、审批 cancelled、resolved 恰好一次、零执行，且保持现有 Task 状态转换协议。
